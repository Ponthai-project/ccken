# 第3分科会（AI-DLCにおける品質保証）ゴール確定と研究の進め方 ― 8/6分科会に向けた検討ガイド

## 0. 大前提と眼目

本資料の目的は、**8/6の分科会で「この分科会のゴール」と「やることやらないこと」を固め切る**ことである。これまでの資料が選択肢を開いて並べる論点集だったのに対し、本改訂は **8/6を第一マイルストーン（締切）として"決め切る"ための検討ガイド**へ性格を変える。何を考え、どの順で詰め、8/6当日に何を決めるかを示す。

**大前提（前回確立・不変）**: 上位の問いは一貫して「AI駆動時代の品質保証をどう成立させるか」であり、**ハーネス（機械的な安全網）はその有力な一手段として相対化して扱う**（品質保証 ⊋ ハーネス）。ハーネスは目的ではなく手段。

**この分科会の眼目（＝存在意義の背骨）**: 本分科会の価値は二層ある。**技術課題**（どのハーネス構成が優れているか・最新技術動向はどうか＝手段）に留まらず、**適用課題**（各社が自社に持ち帰り、自社の品質保証部門・経営を「AI-DLCで品質は落ちない」と納得させられるか＝目的）にこそ本丸がある。**技術課題 < 適用課題** ― 優先すべきは後者。この分科会が答えを出したい象徴的な問いは、**「AI-DLCの導入で品質下がるんでしょ？」に対し、根拠をもって"NO"（むしろ品質は担保できる）と言えるようにする**ことである。最新技術動向の解説で終わらせず、各社が社内を説得できる材料まで到達させる。

**検討フロー（本資料はこの順で貫く）**

## 1. 現状診断 ―「ふわっとしている」の正体

たたき台（`やることやらないこと.md`）は**品質保証という上位問題に正面から向き合えている**点で芯は良い。品質懸念の洗い出し・各社の現行リリースクライテリア調査・品質の3軸分解と、射程は正しい。エンプラ実務（「早く安くなる分、品質が落ちるのでは」）を起点にした出口意識もある。

にもかかわらず「やることやらないこと」が固まらないのは、**個々の作業項目は並んでいるのに、それらが何のゴールに奉仕するのかが言語化されていない**からである。ゴール（何を目指し何を成すか）が未定のまま、やる/やらないを仕分けようとしている ― **順序が逆**なのが「ふわっと感」の正体だ。

| 症状 | 根本原因 |
|---|---|
| 「ハーネスを軸に」と「品質保証全体」が同居し、どちらが主か不明 | **スコープ（品質保証のどこまで扱うか）が未線引き** |
| PoC・ツール選定を急ぐ一方、成果物像が定まらない | **ゴール（成果物・成功基準）が未定義**のまま手段（技術課題）の議論に入っている |
| 「あとで決めること」に本質的問い（3軸・依存度・PoC規模）が滞留 | ゴールが決まれば従属的に決まる問いを、独立問題として抱えている |
| 技術動向・ハーネス構成の話に流れがちで、出口が見えにくい | **適用課題（各社が持ち帰り社内を"品質は落ちない"と納得させる）という目的が背骨に据わっていない**（第0節） |

**処方箋**: 仕分け（フロー③）の前に、まず**ゴールを5要素に分解して言語化する（フロー①）**。ゴールが定まれば「それに奉仕する作業＝やること」「奉仕しない作業＝やらないこと」が論理的に決まる。次節がその中核。

## 2. ゴールを定める枠組み（今回の中核）― 8/6までに答えを出す5つの問い

この分科会のゴールを次の**5要素**に分解する。各要素は「8/6までに各社・分科会で答えを出すべき問い」である。5つが埋まればゴールが言語化でき、やることが定まり、外れるものがやらないことになる。**5要素すべてを貫く背骨は「技術課題 < 適用課題」＝各社が持ち帰り、自社の品質保証部門・経営を"AI-DLCで品質は落ちない"と納得させられること**（第0節）。①対象・②成果物・④成功基準は特にこの適用課題の色を濃く持たせる。

| # | 要素 | 8/6までに答える問い | 仮置き（叩き台・議論の出発点） |
|---|---|---|---|
| ① | **対象と課題** | 誰の・何の課題を解くのか | AI-DLCを導入する**大企業**が直面する「早く安くなる分、品質が落ちるのでは」という**品質懸念**、および**それを自社の品質保証部門・経営に問われたとき"NO（落ちない）"と根拠をもって示せない**という適用の壁に答える |
| ② | **成果物** | 何をアウトプットとして出すか | **各社が持ち帰って社内（品質保証部門・経営）を説得できる材料**。**品質懸念への回答集（"品質下がるんでしょ？"へのNO論拠＝社内説得の背骨）を前段・主軸**に据え、設計ガイドラインで裏づけ、実証データで強化する三層構成（岐路4の三層を"社内説得の根拠"として意味づけ直す） |
| ③ | **スコープ** | 品質保証のどこまで扱うか | **「中」（品質定義〜リリース判定〜機械的検証ゲート）を仮置き推奨**（第3節で詳述） |
| ④ | **成功基準** | 何をもって成功と言えるか | **各社が自社の品質保証部門・経営に対し「AI-DLCで品質は落ちない（むしろ担保できる）」と根拠をもって示せるようになる**こと（＝各社のリリース基準・品質ゲート見直しの判断材料になることは、その手段） |
| ⑤ | **独自性** | 我々（CC研）ならではの強みは何か | **各社の実リリース基準への内部アクセス**と**実機検証（一次データ）**＝二次情報でなく"自社を説得できる一次根拠"を作れる |

**技術課題は手段、適用課題が目的**: ①〜⑤の中で技術要素（実機比較・最新ツール動向）はあくまで**②成果物と④成功基準（社内を納得させる根拠）に効くか**で価値が決まる。「どの構成が技術的に優れているか」の答えも、「だから自社の品質は落ちないと言える」まで接続して初めて成果となる。

### ゴール記述の穴埋めテンプレ（各社が8/6前に埋めてくる）
> 本分科会は、**＿＿＿（①対象）** が **＿＿＿（①課題）** を抱える状況に対し、**＿＿＿（②成果物）** を通じて、各社が **＿＿＿（持ち帰り先＝自社の品質保証部門・経営）** に **＿＿＿（示したい結論。例:「AI-DLCで品質は落ちない／むしろ担保できる」＝NO）** と **＿＿＿（④成功基準の到達状態）** できるようにすることを目指す。扱うスコープは **＿＿＿（③狭/中/広）**、我々の強みは **＿＿＿（⑤独自性）** である。

### たたき台文（上記の仮置きで埋めた例。8/6の議論の出発点）
> 本分科会は、**AI-DLCを導入する大企業** が **「早く安くなる分、品質が落ちるのでは」という品質懸念** を抱える状況に対し、**品質保証の推奨構成＋設計ガイドライン（＋"品質下がるんでしょ？"への回答集）** を通じて、各社が **自社の品質保証部門・経営** に **「AI-DLCで品質は落ちない、むしろ担保できる」（＝NO）** と **根拠をもって示せる** ようにすることを目指す。扱うスコープは **①②③（品質定義〜リリース判定〜機械的検証ゲート、＝中）**、我々の強みは **各社の実リリース基準への内部アクセスと実機検証（自社を説得できる一次根拠）** である。

**使い方**: 各社はこのテンプレの空欄に自案を入れて8/6に持ち寄る。空欄が割れた要素こそ8/6で合意すべき論点。全空欄が埋まり合意できれば、この分科会は「ふわっと」を脱する。

## 3. スコープと下位の論点 ― スコープを起点に、従属論点を仕分ける

ゴール5要素のうち **③スコープが全ての起点**。ただし②成果物は大枠（C・B・Aの三層構成）が既に方向づけ済み（第2節②）であり、スコープが決めるのは**各層の比重**（どこまで厚く書き込むか）。独自性・下位論点の重さも同様にスコープに従属して連動する。

### 3-1. スコープの全体マップ（品質保証 ⊋ ハーネス）
まず品質保証が包含する領域を俯瞰し、各領域が**ハーネス（機械的検証ゲート）の守備範囲か**を示す。ハーネスが中核を担うのは③のみ。

| 品質保証の領域 | 中身 | ハーネス（機械的検証ゲート）の守備範囲 |
|---|---|---|
| ① 品質の定義・目標 | 何をもって品質とするか（再現性・正確性・責任等の価値づけ） | **外側**（定義は所与として受け取る） |
| ② リリース判定基準・検収判断 | 出荷可否のクライテリア、受け入れ判断 | **一部のみ機械化**（最終判断は人に残る） |
| ③ 機械的検証ゲートによる自動検知・停止 | 多層ゲート・自動テスト・SAST/Linter・AIレビュー等 | **中核**（ハーネスの主戦場） |
| ④ 非機能品質（性能・保守性・信頼性）の作り込み | 品質を設計段階で作り込む | **検知はできるが作り込みは外** |
| ⑤ レビュー・品質文化・プロセス品質 | 人のレビュー、品質意識、工程へのゲート配置 | **外側**（分科会②プロセス・④人と組織と接続） |

→ **「ハーネスを軸にする」（たたき台line2）は③に賭ける選択**であって、品質保証全体を代表しない。この一手段を無条件の前提とせず、下記のスコープ選択として開く。

### 3-2. スコープの選択肢（8/6で狭/中/広を決める）
| スコープ | 扱う領域 | メリット | デメリット | 向く場合 |
|---|---|---|---|---|
| **狭**（ハーネス集中） | ③中心（＋②の機械化部分） | 深く独自性が出る。実機実証で一次データ。個別版デッキがそのまま設計図に | 品質保証の一断面に留まり「③に矮小化した」と見られるリスク | 実証で差別化したい／一点集中したい |
| **中**（ハーネス＋クライテリア＋品質定義）★仮置き推奨 | ①②③ | 経営の品質懸念（①②）〜機械的検証（③）を一本で貫ける。看板と独自性を両立 | ①②の議論が広がる分、実機の深さは削られる | **最有力の落とし所**。品質保証の看板と独自性を両立 |
| **広**（品質保証全体の再設計） | ①〜⑤ | 網羅的で全体像を描ける | 浅くなりやすい。④⑤で分科会②④と重複増 | 全体俯瞰優先／統合体制がある |

**★仮置き推奨は「中」**。理由: ①②を含むことで「品質保証」の看板（＝大企業の品質懸念への回答）を保ちつつ、③で実機の独自性も残せる。広く取るほど④⑤で**分科会②（開発プロセス）・④（人と組織）との重複が増す**ため、スコープ決定は②④との境界すり合わせ（第7節）と一体で行う。ただし最終決定は8/6で研究会が下す。

**全スコープ共通の設計原則**: 成果物は個別ツールの優劣でなく「**構成パターン×評価軸**」で語る（陳腐化耐性を確保）。

### 3-3. 下位の論点（岐路1〜4）― 8/6で全部決めなくてよい
スコープ（③）が決まった後に詰める従属的な論点。**8/6はゴール・スコープ合意を最優先とし、下位論点は「方向づけ」または「宿題化」で足りる**。

**下位論点を貫く取捨基準**: 岐路1（実機比較）・岐路3-B（最新ツール/文献調査）はいずれも**技術課題**。これらは目的ではなく手段であり、**「適用課題（各社が社内を"品質は落ちない"と納得させられる根拠になるか）」にどう効くか**で踏み込み度・優先度を決める。技術的に優れた構成を突き止めても、社内説得の論拠に接続できなければ成果は半分。

| 下位論点 | 要点 | 選択肢（推奨） | 8/6での扱い |
|---|---|---|---|
| **岐路1: 実機検証の踏み込み度** | PoCをどこまでやるか | A本格実機比較／B事例＋ガイド中心／**C ハイブリッド（1レイヤ試走→A/Bへ寄せる）** | **方向づけのみ**（Cを初期スタンスに、9月試走で確定） |
| **岐路2: 品質の定義軸** | 3軸と10項目/多層ゲートの接続 | A3軸／B10項目/多層ゲート／**C 2層接続（3軸＝価値軸↔10項目＝測定軸）** | **宿題化**（対応表ドラフトを担当1名に） |
| **岐路3: 調査の主眼** | ヒアリングか文献か | A各社クライテリア/実態ヒアリング／B文献・事例／**C 両輪（文献で型→ヒアリングで実態突合）** | **分担の初期割り**（メンバー数次第） |
| **岐路4: 成果物の主軸** | 何を本紙にするか | A実証レポート／Bガイドライン/チェックリスト／C. 懸念回答集／**推奨=Cを前段・主軸（社内説得の背骨）に据え、Bで裏づけ、Aで強化する三層** | ②成果物の**大枠は方向づけ済み**（第2節②に反映）。各層の比重はスコープに従属し8/6以降に確定 |

## 4. 『やることやらないこと』の固め方 ― 確定/保留/除外の3分類

ゴール・スコープ確定後、たたき台の各項目を **確定（やる）／保留（仮説・スコープ次第）／除外（やらない）** に振り分ける。判定基準は単純: **仮置きゴール（第2節たたき台文・スコープ「中」）に奉仕するか**。

以下は仮置き（スコープ「中」）での**分類例＝叩き台**。8/6でスコープが動けば保留項目の帰属も動く。

| 分類 | たたき台の項目 | 判定理由 |
|---|---|---|
| **確定（やる）** | 大企業の品質懸念の洗い出し・ギャップ整理 | ①対象・課題そのもの。中スコープの起点 |
| | 各社の現行リリースクライテリア洗い出し（AI利用有無問わず） | ⑤独自性（内部アクセス）＋②領域。中スコープの核 |
| | 事例調査は（実施する分について）必ず示唆・提言まで昇華させる＝**出口姿勢の確定** | ④成功基準（各社の判断材料）に直結する出口 |
| | 第1分科会（コンテキスト）・第2分科会（ループ）との境界すり合わせ | スコープ線引きと不可分。第7節と一体 |
| | やらないこと含めた全体感の整理 | 本資料の営み自体。8/6のアウトプット |
| **保留（仮説・スコープ次第）** | 品質に直結するハーネスを軸にする | スコープに従属: 狭=中心採用／中=③として位置づけ／広=相対化 |
| | 世の中事例で品質がどう変わったか整理 | **実施範囲・比重（岐路3の分担）は保留**。実施する分は上記「出口姿勢の確定」（提言まで昇華）に従う |
| | 検証ツールを絞ったメンバーで試す | 岐路1（PoCやるか）に従属。ただし**ツール棚卸しは確定（宿題）** |
| | PoC実施と規模感 | 岐路1。9月試走の手応えで確定 |
| | 品質を再現性・正確性・責任の3軸に分解 | 岐路2。2層接続なら実施、対応表は宿題 |
| | 評価対象の最終決定→開発プロセス全体 | スコープと題材選定に従属 |
| **除外（やらない）** | 特定ベンダー（AWS AI-DLC等）の型をそのまま採用・推奨 | 独自性⑤と矛盾、研究の中立性 |
| | 品質に直結しない安全側ガードレール（AIがDB破壊等） | ①課題（品質懸念）の外 |
| | 実データの管理方法・データの持ち方 | 第1分科会の領域 |
| | LLM自体の性能比較 | 手段の優劣であり品質保証の問いでない |
| | 人/組織の品質評価力（リテラシー・レビュー人材） | 第4分科会の領域 |

**この表の使い方**: 8/6でゴール・スコープを合意 → この分類を叩き台に「保留」を一つずつ確定/除外へ動かす。保留の多くは下位論点（岐路1〜4）に紐づくので、その場で決め切れないものは宿題化して先へ進む。
