# 第3分科会（AI-DLCにおける品質保証）研究の進め方 ― AI-DLCを土台とした4段フローと8/6キックオフ

本資料はこれまで、たたき台（`やることやらないこと.md`）の各項目が仕分けられない「ふわっと感」を解消するため、論点を開いて並べる**論点集**として、ゴール5要素の言語化・スコープ三択（狭/中/広）を軸に構成してきた。検討を重ねた結果、進め方そのものが**4段の研究フロー**として確定し、ハーネスの出発点もAWS公開OSS「AI-DLC」を土台とする方針が固まった。本資料は論点集から**実行ガイド**へ再度性格を転換し、以下の4段フローに沿って全面改訂する。

---

## 0. 大前提と方針転換

**背骨（不変・一字も変えない）**

本分科会の存在意義は3層構造で不変である。

1. 上位の問いは一貫して「AI駆動時代の品質保証をどう成立させるか」であり、**ハーネス（機械的な安全網）はその有力な一手段として相対化して扱う**（**品質保証 ⊋ ハーネス**）。ハーネスは目的ではなく手段。
2. 本分科会の価値は**技術課題**（どのハーネス構成が優れているか・最新技術動向はどうか＝手段）に留まらず、**適用課題**（各社が自社に持ち帰り、自社の品質保証部門・経営を「AI-DLCで品質は落ちない」と納得させられるか＝目的）にこそ本丸がある。**技術課題 < 適用課題** ― 優先すべきは後者。
3. この分科会が答えを出したい象徴的な問いは、**「AI-DLCの導入で品質下がるんでしょ？」に対し、根拠をもって"NO"（むしろ品質は担保できる）と言えるようにする**ことである。最新技術動向の解説で終わらせず、各社が社内を説得できる材料まで到達させる。

**方針転換（今回の確定事項）**

これまでの資料は「ゴールを5要素に言語化する」ことを検討の中核に置いていたが、進め方そのものが以下の**4段の研究フロー**として確定した（第1節）。あわせて、ハーネスの出発点を白紙から選定するのではなく、**AWSが公開したOSSワークフロー「AI-DLC」（awslabs/aidlc-workflows）を共通の土台として据える**方針へ転換する。

これは「特定ベンダーの型をそのまま採用・推奨する」ことではない。AI-DLCはハーネス中立（特定ハーネス・特定LLMに非依存）なOSSであり、われわれはこれを**共通の実験台・出発点**として使い、その上に「制御できない品質をどう担保するか」という独自の検討を積み上げる。採用・推奨するのはわれわれの結論（Step4の担保策）であって、AI-DLCという型そのものではない。整合ロジックの詳細は第2節で書き切る。

参照: [やることやらないこと.md](./やることやらないこと.md) ／ [研究の進め方.md](../01_部会全体/研究の進め方.md) ／ [分科会3_品質保証_インセプションデッキ.md](../../personal_doc/分科会インセプションデッキ/分科会3_品質保証_インセプションデッキ.md) ／ [AI駆動開発における品質評価・品質担保の整理.md](../../personal_doc/AI駆動開発における品質評価・品質担保の整理.md)

## 2. なぜAI-DLCを土台にするのか ― 中立性との整合

背骨（第0節）は「ハーネスは目的でなく手段」であり、独自性は「各社の実リリース基準への内部アクセス」と「一次データによる実機検証」に置いてきた。AI-DLCを土台に据えることが、この不変の方針・独自性と矛盾しないかを正面から整理する。

### 2-1. 「そのまま採用・推奨」と「共通の土台として使う」の峻別

現行の`やることやらないこと.md`が除外していたのは「特定ベンダーの型を**そのまま自分たちの型として採用・推奨する**こと」である。今回の方針転換で行うのは、OSSのAI-DLCを**共通の実験台・出発点**として使い、その上に「制御できない品質の担保策」という独自の価値を載せることであり、両者は別レイヤーにある。

| レイヤー | 現行が除外した行為 | 今回行う行為 |
|---|---|---|
| ゴール（結論として何を推奨するか） | AI-DLCの型をそのまま採用・推奨 | **対象外**（結論はStep4の担保策の集積） |
| 手段（検討をどこから始めるか） | ― | AI-DLCを共通の出発点として使う |

採用・推奨（ゴール）と土台・出発点（手段）は別レイヤーであり矛盾しない。「ハーネスは目的でなく手段」という背骨に、AI-DLC採用は具体的な形を与えるにすぎない。

### 2-2. AI-DLCの性質そのものが中立性を担保する

AI-DLCは`core/`（共通ステージ定義・ナレッジ・ツール・センサーの単一編集源）と`harness/`（各ツール固有アダプタ）、`dist/`（build scriptがcoreから各ハーネス向け配布物を自動生成）から成る「**One core, many harnesses**」構造を持つ。対応ハーネスはClaude Code、Kiro（IDE/CLI）、Codex CLI、Amazon Q Developer（`.amazonq/rules/`）、Cursor（`.cursor/rules/.mdc`）、Cline（`.clinerules/`）に及び、GitHub CopilotもRFCで検討中とされる。LLM・IDEに非依存で、同一の品質ルールを全ハーネス上で同一実行できる設計である。

つまりAI-DLCは特定製品にロックインしないharness-neutralなOSSであり、「AI-DLCベース＝ベンダー中立性の放棄」という等式は成立しない。**AI-DLCはハーネス中立なOSSであり、固定解ではなく共通のたたき台として使う**、という位置づけを本分科会の公式見解とする。

### 2-3. 独自性⑤の再定義

現行の独自性（各社の実リリース基準への内部アクセス＋実機検証の一次データ）はそのまま活かす。これに加え、**AI-DLCという共通の土台の上で、制御できない品質をどう担保するかを各社共通項ベースで設計すること**を独自性の核として加える。

世の中にAI-DLCの紹介記事・技術解説は既に多い。しかし「AI-DLCが機械的に制御しきれない品質を、エンプラ各社共通の物差しでどう埋めるか」を扱った検討は見当たらない空白地帯であり、ここにこそ本分科会の独自価値がある。共通の土台を採用することは独自性を毀損するどころか、比較のベースラインが揃うことで独自性を強化する。

> **一言でいえば**：独自性は「土台の選択」に宿るのではなく、「土台の上に何を載せるか（Step4）」に宿る。

## 3. Step1: AI-DLCハーネスを据える

### 3-1. 何を据えるか

公開Gitリポジトリ [awslabs/aidlc-workflows](https://github.com/awslabs/aidlc-workflows)（AWSがOSSとして公開する適応型ワークフロー）を、本分科会の共通実験台として使う。参考: [AWSブログ：Open-sourcing adaptive workflows for AI-Driven Development Life Cycle](https://aws.amazon.com/blogs/devops/open-sourcing-adaptive-workflows-for-ai-driven-development-life-cycle-ai-dlc/)、[Building with AI-DLC using Amazon Q Developer](https://aws.amazon.com/blogs/devops/building-with-ai-dlc-using-amazon-q-developer)。

### 3-2. 三フェーズ構造

| フェーズ | 内容 | ゲート（人間承認） |
|---|---|---|
| **Inception**（WHAT/WHY） | 要件分析 → ユーザーストーリー → 計画 → アプリ設計 → ユニット生成 | 各ステージ完了後、人間がartifactをレビュー・承認（必須） |
| **Construction**（HOW） | 機能設計 → NFR要件 → NFR設計 → インフラ設計 → コード生成 → ビルド・テスト | コード生成後、静的解析/Lint結果を人間が確認してから進行 |
| **Operations**（デプロイ・監視） | 公開リポジトリ上では placeholder for future（詳細未実装）と明記 | 未整備。将来拡張の余地として正直に扱う |

全フェーズの遷移に人間承認が必須という設計思想は"Always in Control"と呼ばれ、「AI提案 → 人間検証・承認 → AI実行」の反復で貫かれる。単純作業では計画をスキップするなど適応的な実行も許容される。なお、AI-DLCが内部でエージェントをどう分担させているかの詳細（役割分担の粒度等）は一次情報で確認しきれておらず、素振りを通じて実態を確認する対象とする。

### 3-3. "素振り"の分担

本格検証（Step3以降）の前に、各社が実際にAI-DLCを手元で動かし、三フェーズ・ゲート構造・拡張ポイント（Code Reviewer、Security、Testing、Resiliency等の各拡張）の実態を掴む。これは第8節の宿題「awslabs/aidlc-workflowsを各自素振り」として位置づけ、Step1の下拵えとする。

### 3-4. 環境構築リスクとの接続

当分科会は環境構築のリードタイムが長い（CI・サンドボックス・複数ハーネスへの対応）ことが従来から課題として認識されている。この工数リスクはStep1の実行可否に直結するため、第9節のリスク管理でStep1に紐づけて追跡する。

## 4. Step2: 各社リリース品質評価項目の共通項抽出

### 4-1. 前提と収集方針

研究参加各社はいずれも大企業であり、リリース品質評価の骨格（何をもって出荷可としているか）における個社仕様の差は、詳細なしきい値や運用の違いはあれど、大枠では小さいと見込む。この前提のもと、各社の評価項目を持ち寄り、共通項を見出す。

収集方法は、各社への直接ヒアリング（CC研の内部アクセスという独自性⑤を活かす）を主体とし、必要に応じて文献・公開事例で型を補う両輪とする（旧・下位論点「調査の主眼」の結論を継承）。

### 4-2. 収集フレーム（共通テンプレ列）

各社の持ち寄りメモは以下の列で統一し、後段Step3の仕分け表にそのまま接続できる形にする。

| 列 | 内容 |
|---|---|
| 評価項目名 | 各社の呼称（例：静的解析基準、テストカバレッジ基準 等） |
| 評価タイミング | 開発中／リリース判定時／リリース後 のいずれか |
| 判定方式 | 機械的しきい値／人間レビュー／両方 |
| AI利用有無での差異 | AI駆動開発特有の追加基準があるか |
| 出典・根拠 | 社内規程／業界基準／自主基準 のいずれか（機微情報は匿名化） |

### 4-3. 共通項テーブル（分類基準）

収集結果を以下の3分類に整理する。品質の価値軸（旧・下位論点「3軸：再現性・正確性・責任」）は、この分類を横断する上位の意味づけとして活用し、独立の検討テーマとしては扱わない。

| 分類 | 定義 | 想定される該当項目（仮） |
|---|---|---|
| **コア**（全社共通） | ほぼ全参加社が同一の考え方で持つ項目 | 静的解析・Lint、テストカバレッジ、セキュリティスキャン、変更履歴のトレーサビリティ |
| **準コア**（過半共通） | 過半数の社が持つが、粒度・運用に差がある項目 | NFR（性能・可用性）の定量基準、レジリエンシ検証 |
| **オプション**（個社固有） | 特定社固有の規程・業界規制に基づく項目 | 業界固有コンプライアンス要件、社内特有の承認フロー |

分類の具体化（項目の実名を埋める作業）は第8節の宿題H1「各社リリース基準の持ち寄り」の結果を待って行う。ここで固まったコア・準コア項目が、Step3の仕分け表の入力列（共通項）になる。

## 5. Step3: 制御できる／できない の仕分け（資料の心臓部）

### 5-1. 母体：品質保証領域×ハーネス守備範囲マップ

Step2の共通項に入る前に、まず品質保証全体が包含する領域を俯瞰し、どこがハーネス（機械的検証ゲート）の守備範囲かを整理する。

| 品質保証の領域 | 中身 | ハーネスの守備範囲 |
|---|---|---|
| ① 品質の定義・目標 | 何をもって品質とするか（再現性・正確性・責任等の価値づけ） | **外側**（定義は所与として受け取る） |
| ② リリース判定基準・検収判断 | 出荷可否のクライテリア、受け入れ判断 | **一部のみ機械化**（最終判断は人に残る） |
| ③ 機械的検証ゲートによる自動検知・停止 | 多層ゲート・自動テスト・SAST/Linter・AIレビュー等 | **中核**（ハーネスの主戦場） |
| ④ 非機能品質（性能・保守性・信頼性）の作り込み | 品質を設計段階で作り込む | **検知はできるが作り込みは外** |
| ⑤ レビュー・品質文化・プロセス品質 | 人のレビュー、品質意識、工程へのゲート配置 | **外側**（分科会②プロセス・④人と組織と接続） |

AI-DLCの三フェーズ・ゲート構造（第3節）は、主に③、一部④の検知に効く。①②⑤はAI-DLCの守備範囲外であり、Step4の担保策研究の対象になる。

### 5-2. 仕分け表の骨格

Step2で固まった共通項（コア・準コア）を1行ずつ、以下の列で仕分ける。

`共通項（Step2由来の評価項目）｜AI-DLCでの制御手段（該当ゲート/エージェント）｜制御度（◎機械的に停止できる／△検知のみ／×ハーネス外）｜不足・ギャップ（Step4送り）`

### 5-3. AI-DLCの実装事実に基づく仕分け（先行整理）

Step2の各社共通項が確定する前でも、AI-DLC自体の機能から判明している範囲で先行して仕分けられる項目は以下の通り。

| 共通項（想定） | AI-DLCでの制御手段 | 制御度 | 不足・ギャップ（Step4送り） |
|---|---|---|---|
| 静的解析・Lint | Code Reviewer拡張（ruff・mypy・bandit等） | **◎** | 検出ルールの妥当性判断は人間に残る |
| セキュリティスキャン | Security拡張のベースラインルール（不合格でブロック） | **◎** | 例外承認の妥当性判断、ベースライン自体の適切性 |
| テスト実行・カバレッジ | Testing拡張（プロパティベーステスト含む） | **◎** | エッジケース網羅性の判定は人間 |
| NFR計測（実行時間・トークン使用量） | Testing拡張 | **◎** | 目標値・閾値そのものの設定 |
| レジリエンシ検証 | Resiliency拡張 | **◎** | 検証シナリオの十分性判断 |
| 成果物フォーマット検証 | Mermaid/ASCII等のフォーマットチェック | **◎** | ― |
| トレーサビリティ・監査証跡 | Audit Log（全入力をISO8601で自動記録） | **◎** | ログの活用・監査プロセスとの接続は運用側 |
| ステージゲート通過 | 各フェーズの必須人間承認ゲート | **◎**（進行制御） | 承認判断の質そのものは人間依存 |
| 品質基準値・閾値の妥当性 | ― | **×** | 業界標準・各社基準との突合が必要 |
| 規則違反時のoverride承認 | ― | **×** | 承認プロセス設計、責任の所在明確化 |
| AI生成テスト/設計の妥当性評価 | ― | **△**（実行はできるが評価は人間） | レビュー基準・チェックリスト整備 |
| 設計パターン選択の是非 | ― | **×** | アーキテクチャレビューの型化 |
| パフォーマンス目標値・トレードオフ判定 | ― | **×** | 各社NFR基準の読み替え |
| レビューの深さ・批評の妥当性 | ― | **×** | レビュー設計ガイドライン |

Step2で固まる各社共通項（コア・準コア）はこの先行整理に照らして再分類し、AI-DLC固有機能でカバーしきれない共通項があれば新規行として追加する。

※役割分担の粒度（どのエージェントが何を担うか）等、一次情報で確認しきれていない部分は「構成からの推測」であり、Step1素振りでの検証対象とする。

## 6. Step4: 制御できない品質の担保策研究（本丸＝適用課題）

Step3で×・△に仕分けられた項目こそ、AI-DLC単体では埋まらない「適用課題」の本体である。これに対する担保策を、以下の観点で研究する。

| 担保策の種類 | 内容 | 対応するStep3のギャップ例 |
|---|---|---|
| 人手レビュー設計 | 何を・誰が・どの深さでレビューするかの型化 | レビューの深さ・批評の妥当性、AI生成テストの妥当性評価 |
| プロセス上のゲート配置 | AI-DLCのゲートに加え、組織側で必要な追加承認ポイントの設計 | override承認、設計パターン選択の是非 |
| トレーサビリティ補完 | AI-DLCのAudit Logを監査・説明責任にどう接続するか | 監査証跡の活用・運用設計 |
| 各社基準の読み替え | 各社固有の閾値・目標値をAI-DLCの計測結果にどう対応づけるか | 品質基準値・閾値の妥当性、パフォーマンス目標値 |
| 社内説得の論拠化 | 担保策の集積を「品質は落ちない」根拠として言語化 | 全項目の最終出口 |

**成果物**：第2節の独自性再定義を受け、成果物は以下の三層構成とする。

1. **品質懸念への回答集**（"品質下がるんでしょ？"へのNO論拠＝社内説得の背骨）を**前段・主軸**に据える。
