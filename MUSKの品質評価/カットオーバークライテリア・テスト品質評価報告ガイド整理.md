# カットオーバークライテリア・テスト品質評価報告ガイド整理

## 1. 目的

本資料は、<File>A30_080_カットオーバークライテリア記載要領.docx</File>と<File>B30_T_60_G_010_テスト品質評価報告ガイド.docx</File>を対象に、次の観点で整理したものである。

- どのような項目を達成する必要があるか
- どの部署・役割が関連するか
- 具体的に何ができれば品質保証ができたといえるか

> **要点**  
> テスト品質評価報告は、テスト終了・次フェーズ移行の妥当性をデータと分析で説明するための資料である。カットオーバークライテリアは、そのテスト品質に加えて、性能・容量、運用、移行、フォールバック、サービスイン直後体制、保守準備、必要な規制対応まで含め、本番移行可否を関係部署が判断するための基準である。

# 3. カットオーバークライテリア記載要領

## 3.1 目的

カットオーバークライテリアは、システムの本番移行可否を判定するための基準である。具体的な評価項目と基準を事前に定め、達成状況を評価することで、作業の積み残しがないこと、または積み残しがあっても本番移行・業務運営上のリスクと対応策が明確であることを示し、案件承認者やユーザ部署等がカットオーバー条件の充足を判断できるようにする。

## 3.2 帳票として明確にする事項

| 区分 | 記載事項 | 確認ポイント |
|---|---|---|
| 評価項目 | 大分類・中分類・小分類・評価項目 | カットオーバー可否を判断できる粒度か |
| 基準 | 基準値・条件・単位 | Yes/No、0件、95%等、達成／未達を客観的に判定できるか |
| 達成日 | 予定日・実績日 | 到達予定と実際の達成日を確認できるか |
| 主担当 | 部署・担当者 | 各評価項目の評価責任が明確か |
| 評価 | 評価時点・評価ランク・予定値・実績値・全体数 | 評価時点ごとの状況を定量的または論理的に説明できるか |
| 確認資料 | 達成状況を確認する資料 | 判定と証跡が結び付いているか |
| 備考 | 課題・対応策・補足・評価対象外理由 | 例外や残課題の理由が説明されているか |

評価ランクは「×：対策必要」「○：実施中」「●：予定どおり完了、ただし残課題あり（キャッチアップ計画策定済）」「◎：完了および目標達成」の4段階で記載する。最終評価では、既に完了している項目も再評価する。

標準項目を評価しない場合は理由を備考欄に記載し、案件特性上必要な項目は追加する。標準項目で不足する場合は「その他」に追加する。

## 3.3 達成すべき評価領域

### 3.3.1 システム品質

- 総合テストの未消化テストケース数
- 外部接続テストの未消化接続先数
- 重要度別の未対応障害件数
- 変更要求の計画未済・対応未済件数
- ユーザ部署による「カットオーバー可能な品質」の評価
- システム品質の総合評価

障害対応残の基準は基本的に0件である。障害残を許容する場合は、各障害の事象、影響範囲、事前検出可否、代替策の有無等に関するリスク評価・対策と、ユーザとの合意状況を明記する。

### 3.3.2 性能・容量

- バッチ処理時間の要件充足
- オンライン応答時間の要件充足
- 運用許容時間帯の要件充足
- ディスク容量、ピーク時メモリ、CPU使用率等のキャパシティ要件充足

### 3.3.3 システム運用・事務運用

- 本番環境のハードウェア・ソフトウェア・ネットワーク構築
- コンフィグレーション管理
- センター運用体制、通常時・障害時の運用手順、運用マニュアル
- ユーザ部署の運用体制、通常運用、バックアップ運用、オペレーション手順
- 業務・事務マニュアル、研修、業務コンティンジェンシープラン
- システム障害発生時手順の検証
- 対象となるPD資料のインシデントポータル掲載

オフサイトバックアップシステムまたは手順書に変更がある場合は、運用管理部署のオペレータが参画し、手順の妥当性を検証する項目が示されている。

### 3.3.4 本番移行切替

- 移行リハーサルの未消化項目
- 移行システム・移行手順の重要度別障害対応残
- 移行計画書の作成
- ユーザ部署を含む移行体制の確立・検証
- 本番移行手順および特殊事務処理の計画・検証
- 移行タイムチャートの作成・検証
- 移行用資源の計画・検証
- システム資源・運用関係資源の本番反映計画・検証
- 本番環境での稼働確認手順
- 初回稼働特別対応
- 移行コンティンジェンシー
- フォールバックの判定ポイント確定と手順検証
- サービスイン直後の照会、障害対応、確認・検証体制
- 初回本番の確認・検証項目と手順
- 移行計画全体の実効性

移行リハーサル着手時は準備状況を評価し、カットオーバー判定時はリハーサル結果を踏まえた評価・見直しが完了しているかを確認する。

### 3.3.5 保守準備

- 保守用テスト環境の確保
- ライブラリー管理手順の確立
- 保守対象ドキュメントの確定・更新
- 変更管理手順の確立
- 保守体制の確立

### 3.3.6 規制対応・その他

制度対象システムの新規導入・改修に該当し、当局事前審査が必要な場合は、当局承認済みであることを確認する評価項目がある。標準項目で不足する場合は、業務リハーサル等の案件固有項目を追加する。

## 3.4 関係部署・役割

| 部署・役割 | 資料に明示された関与 |
|---|---|
| 主担当部署・担当者 | 各評価項目を評価する主体として帳票に設定 |
| ユーザ部署 | システム品質評価、業務・事務運用、研修、コンティンジェンシー、移行体制、サービスイン直後体制等を確認 |
| 運用管理部署 | センター運用の引継ぎ、通常時・障害時手順、必要時のオフサイト切替手順検証に関与 |
| 案件承認者 | 評価結果をもとにカットオーバー条件の充足を判断 |
| システム企画部署 | MUTB領域で経済安全保障上の当局事前承認が必要な場合の確認先 |
| 品質管理責任者等 | 未修正障害を許容する際の合意・責任範囲に関係 |

上表は資料に役割または確認先が明示されている範囲で整理した。案件固有の正式な承認経路・部署名は、この記載要領だけでは確定できない。

## 3.5 「リリース可能」といえる状態

- [ ] 標準項目と案件固有項目に、客観的な基準値・判定条件がある
- [ ] 評価時点ごとの予定値・実績値・評価ランクが記録されている
- [ ] 各判定に確認資料がひも付いている
- [ ] システム品質、性能・容量、運用、移行、保守準備が評価済みである
- [ ] ユーザ部署がカットオーバー可能な品質と評価している
- [ ] 移行計画・手順・所要時間・体制・資源が検証されている
- [ ] フォールバック判定ポイントが確定し、手順が検証されている
- [ ] サービスイン直後の確認・障害対応体制が確立している
- [ ] 残課題がある場合、リスク・対策・キャッチアップ計画・合意状況が明記されている
- [ ] 必要な規制手続が完了している
- [ ] 案件承認者・ユーザ部署等が本番移行可能と判断できる

# 4. テスト品質評価報告ガイド

## 4.1 目的

テスト品質評価報告書は、テストの終了判断および次フェーズへの移行可否判断に使用する。主な構成は「総評」「テスト実施状況」「合否判定結果」「判定結果根拠」「追加施策」「参照資料」であり、特に、なぜその判定に至ったかを合理的に説明する「判定結果根拠」が重視されている。

本ガイドは各案件での適用が望ましいとされる一方、準拠の程度は案件内容等を踏まえて案件計画時に個別判断できる。

## 4.2 評価前に収集・整理するデータ

- 進捗管理データ等の管理情報
- テスト計画書等の設計ドキュメント
- モニタリングで使用した測定メトリクス値と評価結果
- 中間評価結果

報告書には、品質指標の予定・実績、各基準の分析・評価、中間評価の要点、追加施策を記載する。基準未達でも条件付き合格とする場合は、合理的根拠が必要である。

## 4.3 達成すべき合否判定基準

| 基準 | 達成すべき状態 | 主な説明内容 |
|---|---|---|
| 0：テスト設計状況 | 網羅性を満たし、対象規模に見合うテスト量であり、非実施領域も監視・評価している | カバレッジ、ケース数・密度、非実施領域の問題有無 |
| 1：テスト実施状況 | 予定テストを全て実施。未実施がある場合は理由・リスク・影響・対策を明確化 | 完了率、予定実績差、残テストケース |
| 2：障害検出状況 | 障害数とテスト量のバランスを確認し、過多・過少等の異常を分析・対策している | 障害件数密度、要件別・機能別・原因別等の分析 |
| 3：障害修正状況 | 原則として全障害を修正。未修正の場合はリスク・対策を示し、関係者間で合意 | 修正完了率、未修正理由、合意証跡 |
| 4：障害修正品質 | デグレードの発生傾向から残存リスクを評価している | デグレード有無、対策、影響、実施時期 |
| 6：障害発生傾向分析 | 各種分析から残存障害を推測し、フェーズ終了判断の妥当性を評価している | 検出状況、収束、再発、水平展開 |

基準5と基準7は、この版では検討対象外とされている。

## 4.4 特に重視される分析

### テスト設計・実施

- 予定値と実績値の差分を可視化する
- テストケース数・密度が管理限界内か確認する
- 網羅性未達の場合は理由、リスク、影響、対策を記載する
- テスト途中で網羅性を変更した場合は理由と変更時期を記録する
- 未実施ケースがある場合は、ケースごとに理由、リスク、影響、対策を記載する

### 障害検出

最低限、障害件数密度、要件別・テストタイプ別・機能別・プログラム別、テストケース密度とのバランス、検出工程別、直接原因・根本原因別等の観点で異常有無を分析する。単一粒度で終わらせず、複数粒度・複数観点で確認し、管理図・ゾーン図・パレート図等による可視化が望ましいとされる。

### 障害修正・残存リスク

- 未修正障害の有無を明示する
- 未修正の場合、障害内容、未修正理由、リスク、対策、合意した品質管理責任者または参照証跡を記載する
- デグレードがある場合、分析結果、実施済み対策、対策後評価、残存リスクの影響範囲・対策・実施時期を記載する
- 検出すべき障害が検出されたか、障害が収束傾向か、再発していないかを分析する

### 水平展開

水平展開が必要なものを全て実施したか、実施後に類似問題が検出されていないかを評価する。詳細一覧では実施範囲を明確にし、不要または範囲限定とした場合は理由を記載することが望ましい。

## 4.5 関係部署・役割

<File>B30_T_60_G_010_テスト品質評価報告ガイド.docx</File>は、部署別の役割分担表を定めていない。明示されているのは、未修正障害を許容する場合に関係者間の合意が必要であり、責任範囲を明確にするため具体的に合意した品質管理責任者を記載すること、または既存の合意証跡を参照することである。

実案件では、少なくとも次の担当を案件計画・体制に合わせて明確にする必要がある。以下は資料内容を実務用に配置した**整理案**であり、ガイドが固定部署名を指定しているものではない。

| 実務上の担当 | 担当する内容の整理案 |
|---|---|
| テスト統括・品質評価担当 | メトリクス収集、分析、総評、合否判定根拠の作成 |
| 各テスト実施チーム | テスト実績、障害情報、原因分析、水平展開結果の提供 |
| PM・PL等のプロジェクト管理者 | 次フェーズ移行判断、残存リスク・追加施策の管理 |
| 品質管理責任者 | 未修正障害を許容する場合の合意・責任範囲の明確化 |
| 関係者 | 未修正障害、リスクおよび対策に対する合意 |

## 4.6 「テスト品質を保証できた」といえる状態

- [ ] テスト終了・次フェーズ移行の合否基準が計画時に定められている
- [ ] 品質指標の予定値と実績値が示されている
- [ ] 網羅性とテスト量の妥当性を説明できる
- [ ] 未実施領域・残テストケースの理由、リスク、影響、対策が明確である
- [ ] 障害件数・密度を複数の粒度と観点で分析している
- [ ] 異常傾向がある場合、原因分析と追加施策を実施し、結果を評価している
- [ ] 障害を原則全件修正している
- [ ] 未修正障害がある場合、リスク・対策・責任者・合意証跡がある
- [ ] デグレードと残存障害のリスクを評価している
- [ ] 障害の収束、再発有無、水平展開結果を評価している
- [ ] 各判定を裏付けるデータ・資料がある
- [ ] 総合判断として、フェーズ終了・次フェーズ移行の妥当性を合理的に説明できる

# 5. 2資料を統合した品質保証の判定

## 5.1 統合判定表

| 判定段階 | 判定内容 | 合格と説明できる状態 |
|---|---|---|
| テスト品質評価 | システムのテスト品質が次フェーズへ進める状態か | 網羅性、実施状況、障害検出・修正、デグレード、残存リスク、水平展開をデータで説明できる |
| カットオーバー評価 | 本番移行・業務運営の準備が整っているか | テスト品質に加え、性能、運用、移行、フォールバック、サービスイン後、保守、規制対応を評価済み |
| 最終判断 | 関係部署がリスクを理解し、本番移行可能と判断できるか | 基準、実績、証跡、残課題、対策、責任者、合意が一貫している |

## 5.2 最終チェックリスト

### テスト品質

- [ ] 品質指標と合否基準が事前定義されている
- [ ] 予定・実績・差分・分析結果が記録されている

### リリース準備

- [ ] 移行計画・リハーサル・体制・手順・時間・資源が検証されている
- [ ] フォールバックと移行コンティンジェンシーが確認されている
- [ ] 初回稼働・サービスイン直後の確認・障害対応体制がある
- [ ] 保守環境、文書、ライブラリー、変更管理、保守体制が整っている
- [ ] 必要な規制対応が完了している

### 証跡・承認

- [ ] 各評価項目に基準値、実績値、評価ランク、確認資料がある
- [ ] 残課題にリスク、影響、対策、期限、責任者がある
