01

なぜHooksか

CLAUDE.mdへの「お願い」と、Hooksの「強制」は根本的に違う。

従来：LLMにお願いする
💬 CLAUDE.md / プロンプト指示
「編集後は必ずprettierを走らせて」と書いても、確率的にしか従わない。会話が長くなるほど忘れる・見落とす・省略することがある。
VS
Hooks：イベントで縛る
⚙️ Hooks（フック）
PostToolUseイベントが発火すれば100%必ずコマンドが実行される。Claudeの気分や記憶に依存しない決定論的な仕組み。

軸は「誰が引き金を引くか」。Hooksはイベントが、スラッシュコマンドは人間が、MCPやsubagentの起動は主にモデル自身の判断が引き金になる。「なぜ自動フォーマットはHooksで縛り、複雑な調査はsubagentに委任するのか」は、この軸で腹落ちする。

02

セッションのライフサイクル俯瞰

資料の背骨・最重要。どのイベントがいつ火を噴くかを一目で。

主フローはSessionStart→UserPromptSubmit→〔PreToolUse→ツール実行→PostToolUse〕×N→Stop→SessionEndの順で必ず一直線に流れる。ツールが呼ばれるたびにPreToolUse→ツール実行→PostToolUseのセットが繰り返され（1回の応答で複数回ツールを使えば、その回数だけ繰り返す）、ツールを一切使わない応答であればこのループはゼロ回のままStopへ進む。

一方、Notification・SubagentStop・PreCompactの3つは主フローの「傍流」で、条件を満たしたときだけ分岐的に発火する。Notificationは権限確認ダイアログの表示や60秒以上の応答待ちアイドル時に、SubagentStopはTaskツール経由で呼び出したサブエージェントの応答が完了した瞬間に、PreCompactは殿が手動で/compactを打つか、コンテキストウィンドウが圧迫されて自動圧縮が走る直前に、それぞれ発火する。

なお、1セッション内で複数回ユーザーが発話すれば、Stopのあと再びUserPromptSubmitに戻ってこの主フロー全体が繰り返される（＝セッションは複数ターンにまたがる）。SessionEndが発火するのはセッションそのものが終了するときの一度きりである。

03

イベント・カタログ

主要9イベントは厚く、拡張イベントは一覧で網羅する。

PreToolUse
発火：ツール実行の"直前"
用途：危険コマンドのブロック、権限チェック、パラメータ検証
ブロック：可 exit2 / permissionDecision:deny で実行阻止
PostToolUse
発火：ツール実行が成功した"直後"
用途：自動フォーマット、lint、変更の監査ログ
ブロック：不可 ツールは実行済み。ただしexit2でエラーをClaudeへフィードバック可
UserPromptSubmit
発火：ユーザーの発話がClaudeに渡される直前
用途：コンテキスト注入（additionalContext）、プロンプト内容の検証・ブロック
ブロック：可 exit2でプロンプト投入そのものを止める
Notification
発火：Claudeが通知を送る時（権限確認・60秒アイドル等）
用途：デスクトップ通知、外部連携
ブロック：不可
Stop
発火：メインエージェントが応答を終えようとする時
用途：未完了タスクの検知、停止前の最終検証
ブロック：可 exit2で停止をブロックし継続させる
SubagentStop
発火：サブエージェント（Task経由）が応答を終えようとする時
用途：サブエージェント成果物の検証
ブロック：可 Stopと同様、exit2で継続させる
PreCompact
発火：会話履歴の圧縮（compact）直前
用途：圧縮前のtranscriptバックアップ
ブロック：不可
SessionStart
発火：セッション開始・再開（startup/resume/clear/compact）時
用途：git状態や開発コンテキストの自動注入（additionalContext）
ブロック：不可 追加コンテキストの注入は可能
SessionEnd
発火：セッション終了時
用途：クリーンアップ処理、終了ログの記録
ブロック：不可

凡例：可＝そのフックの実行結果（exit code / JSON出力）でClaudeの挙動を止める・変えることができる。不可＝原則として観測・副作用用途で、Claude本体の処理フローを止める力はない。

04

設定の書き方（settings.json）

matcher → hooks[] → {type, command, timeout} の入れ子構造。

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR/.claude/hooks/format.py\"",
            "timeout": 30
          }
        ]
      }
    ]
  }
}
matcher＝どのツール呼び出しに反応するか hooks[]＝実行するコマンドの配列（複数登録可） command / timeout＝実行内容と秒単位のタイムアウト

この例はPostToolUseに登録したフック。matcher: "Edit|Write"でEditツールまたはWriteツールの呼び出し後だけに反応し、hooks配列の中にtype: "command"（現状はcommand型のみ）、実行するcommand、timeout（省略可、超過すると強制終了）を書く。commandは$CLAUDE_PROJECT_DIRで絶対パス参照すると堅牢（詳細は09）。フック本体（format.py側）は06で見る入力JSONをstdinで受け取り、tool_input.file_pathから対象ファイルを判定する設計にすると環境非依存になる。

3階層の設定ファイル

階層パス用途
ユーザー全体~/.claude/settings.json全プロジェクト共通の個人設定
プロジェクト共有.claude/settings.jsonチームで共有・commit対象
プロジェクトローカル.claude/settings.local.json個人のローカル設定・.gitignore対象
3階層は上書きではなく「マージ・合算」される。同じイベントに複数階層でフックを登録すると両方とも実行される（＝二重発火に注意。09で詳述）。
05

matcherの当て方

「どのツール／どの条件で発火するか」を決めるパターン。

ツール名の例：

Edit Write Bash Read Task
matcherの書き方意味
EditEditツールの呼び出しだけに一致（完全一致）
Edit|WriteEditまたはWrite（正規表現のOR）
Notebook.*正規表現として評価される（柔軟なパターンマッチ）
（空文字／省略）すべてのツール呼び出しに一致
⚠ イベントによってmatcherの「意味」自体が変わる
イベントmatcherが表すもの
PreToolUse / PostToolUseツール名（Edit, Write, Bash 等）
PreCompactmanual（/compact手動実行）またはauto（自動圧縮）
SessionStartstartup / resume / clear / compact

さらにmatcherは大文字小文字を区別する。"edit"と書いてもEditツールにはマッチしない。

06

入力JSON（stdinで受け取る）

フックはこのJSONを標準入力から読み、判断材料にする。

{
  "session_id": "abc123...",
  "transcript_path": "/home/user/.claude/projects/.../session.jsonl",
  "cwd": "/home/user/project",
  "hook_event_name": "PreToolUse",
  "permission_mode": "default",
  "tool_name": "Write",
  "tool_input": {
    "file_path": "/home/user/project/notes.txt",
    "content": "Hello World"
  },
  "tool_use_id": "toolu_01ABC..."
}
共通フィールド（全イベントに存在） イベント固有フィールド（PreToolUseの場合）

これはPreToolUse発火時の入力例。共通フィールド（session_id, transcript_path, cwd, hook_event_name, permission_mode）はどのイベントでも必ず含まれる「土台」。イベント固有フィールド（PreToolUseならtool_name, tool_input, tool_use_id）はイベント種別ごとに変わる。フック側のスクリプトは、まずstdin全体をJSONとして読み込み、hook_event_nameで分岐し、必要な固有フィールドを取り出す、という実装が定石になる。次の07では、このJSONを読んだ上で「何を返すか（出力・制御）」を対で見る。

07

出力・制御（フックからClaudeへ）

難所。exit codeとJSON出力の2系統で挙動を制御する。

exit 0
✅ 通過
正常終了として処理を継続。stdoutにJSONを出力すればその内容が処理される（UserPromptSubmitではstdoutの文字列がそのままcontextに追加される）。
exit 2
⛔ ブロッキングエラー
stderrの内容がClaudeに渡される。イベントに応じて処理そのものを止める（詳細は下表）。
exit N（N≠0,2）
⚠ 非ブロッキングエラー
エラーとして記録されるが、Claudeの処理は止めずに継続する。
イベントexit 2 の効果
PreToolUseこれから実行しようとしたツール呼び出しを止める
UserPromptSubmitプロンプトのClaudeへの投入そのものを止める
Stop / SubagentStop応答を終えて停止しようとする動作自体を止め、Claudeに継続させる
＋

JSON出力による上級制御

{"decision":"block","reason":"..."}

汎用のブロック指定。reasonの文字列がClaudeに伝わり、次の行動判断の材料になる。

hookSpecificOutput.permissionDecision

PreToolUse専用。"allow" / "deny" / "ask"の3択でツール実行そのものを制御できる。

hookSpecificOutput.additionalContext

UserPromptSubmit・SessionStart用。任意の文字列をClaudeのコンテキストに注入できる（git branch名の自動挿入等、08のレシピ⑥参照）。

📥 06：stdinのJSONを
「読む」
📤 07：exit code / stdoutで
「返す」

06で受け取った入力JSON（tool_input等）を判断材料に、07の出力方式で応答する——この「読む→返す」の一往復が、フック1回の実行サイクルの全体像になる。exit codeは粗い制御（通す／止める／継続）、JSON出力は細かい制御（許可・拒否・保留・理由・コンテキスト注入）と役割が分かれている点を押さえておく。

08

活用レシピ集

〔イベント × matcher × 何をするか〕の3点セットで覚える。

1🎨 自動フォーマット
PostToolUse × matcher: "Edit|Write"
保存直後にprettier / gofmt等を自動実行。フォーマット崩れを人間がレビューする手間をゼロにする。
2🔍 lint／型チェック
PostToolUse × matcher: "Edit|Write"
lint・型チェックを実行し、失敗したらexit 2でstderrにエラー内容を返す。Claudeがそのエラーを見て自ら修正に向かう。
3🛡 ファイル保護
PreToolUse × matcher: "Edit|Write|Bash"
.envや.git/配下等の重要ファイルへの書き込み・削除をpermissionDecision:"deny"で機械的にブロック。
4🔔 デスクトップ通知
Notification / Stop × matcher: なし
権限確認待ちや応答完了のタイミングでOS標準の通知を飛ばし、離席中でも気づけるようにする。
5🧾 監査ログ
各種イベント × matcher: なし
受け取った入力JSONをそのままログファイルに追記。「いつ・何のツールが・何をしたか」を後から機械的に追える証跡になる。
6📌 コンテキスト注入
UserPromptSubmit / SessionStart × matcher: なし
現在のgit branch名や直近のCIステータス等をadditionalContextで自動的にClaudeへ渡し、「今どのブランチで作業中か」を毎回説明する手間を省く。
殿の環境（Windows/PowerShell）は要注意ポイントが多いぞ
09

落とし穴＆Windows作法

公式ドキュメントで明記されている、実務で踏みがちな地雷。

⚠ Windows差異（最重要）

フックのshell-form command（"command":"..."という文字列指定）は、Windowsでは既定でGit Bashを起動して実行される。つまりコマンドはGit Bash（POSIX風シェル）前提で書く必要がある。公式のサンプルに頻出するjqはWindowsに標準搭載されていないため、公式はPython / Node.jsでのJSONパースを推奨している。パスは${CLAUDE_PROJECT_DIR}を使って絶対参照させると、cwdの違いに左右されず堅牢になる。

{
  "type": "command",
  "command": "python3 \"${CLAUDE_PROJECT_DIR}/.claude/hooks/check.py\""
}

どうしてもPowerShellのコマンドを使いたい場合は、shell formの中から直接呼び出す形にする：

{
  "type": "command",
  "command": "powershell.exe -Command \"Get-Content $env:CLAUDE_PROJECT_DIR/notes.txt\""
}
🔀 並列実行とマージ発火

同一イベントに複数フックが登録されていれば並列実行される。さらに04で見た通りuser/project/localの3階層はマージ・合算されるため、同じような処理を複数階層で重ねて登録していないか（＝二重発火）を定期的に見直す。

🐢 レイテンシの上乗せ

フックは登録した対象イベントの毎回走る。重いlintやテストを全PostToolUseに付けると、Edit1回ごとに数秒〜数十秒待たされることになる。matcherで対象を絞る、重い処理は非同期化する等の工夫が要る。

🔁 無限ループ注意

Stopフックが「まだ作業が残っている」と判断してexit2で継続させ続けると、Claudeが新たな作業を延々と生み出す無限ループに陥りうる。入力JSON中のstop_hook_active等のフラグを見て、自己防御的に多重発火を打ち切る実装にする。

10

セキュリティ＆デバッグ

「任意コード実行」である以上、最後は自己責任で確認する。

ユーザー権限での任意実行

フックは殿自身のユーザー権限で任意のシェルコマンドを実行する。確認なしに自動実行されるため、共有・流用する前に内容を必ずレビューする。

セッション開始時にスナップショット

フック定義はセッション開始時点の内容がスナップショットされる。実行中にsettings.jsonを書き換えても即時反映されない＝セッション中に悪意あるフックへすり替えられる攻撃を防ぐ設計。

denyは常に優先される

denyルールはbypassPermissionsモードでも有効（強制ルールとして機能する）。一方allowルールは既存のdenyルールを緩和できない（制限を厳しくする方向のみに働く）。

デバッグ動線

/hooksコマンドで現在登録されているフック内容をread-only確認できる。挙動が怪しい時はclaude --debugで詳細ログを見る。

JSON汚染対策

シェルのprofile（.bashrc等）にechoを仕込んでいると、その出力がフックのJSON入出力に混ざりパース不能になることがある。echoはinteractive時のみに限定するよう条件分岐しておく。
