## 0. サマリ(先に結論)

- 研究の軸は **「AI駆動開発における品質保証」**。ハーネス(CLAUDE.md / Skills 等)を主な手段として扱う。
- 7/23の議論で **アプローチが二段構えに転換** した。
  - **トップダウン**: 各社の品質基準・リリース判定基準を持ち寄り、「AI駆動開発の適用を阻む要件(=適用課題)」を明確化する
  - **ボトムアップ**: ハーネスの有無で品質がどう変わるかを実際に検証する
- 従来の「ハーネスありき」から、**「品質課題起点 → ハーネスで解く」** へ順序が変わった点が最大の変化。
- 併せて「やる/やらないを並べる前に、まず仮説を立てる」という進め方の原則が確認された。
- **評価対象は「開発プロセス全体」に決定**(コード等の特定成果物に絞らない)。
- 第1・第2分科会との境界線すり合わせが「あとで決めること」から **「やること」に格上げ**。

## 1. 研究テーマと背景

### 1.1 部会全体のテーマ

**「AI時代の『アジャイルとウォーターフォール』の進化に関する研究」**(第3研究部会 / 31名)

キックオフ資料(資料3)における課題認識:

1. 「AI-Ready」化の遅れ — 組織としてAIを継続活用する環境・データ・知識の準備不足
2. **Spec-Driven開発を支える形式知の不足** — AIが正確に実装できる粒度で要件・仕様が形式知化されておらず、**複雑な仕様のシステム開発および品質保証が困難**
3. AIOpsを見据えたDevOps統合の未整備

→ このうち **2の後半(品質保証)** が第3分科会の担当領域。

### 1.2 第3分科会のテーマ

**「AI品質保証 〜AI生成物を信頼して利用するための品質保証モデル〜」**

**なぜここにいるのか(7/10集中検討会での整理)**

- 理想は「AIに全部任せて開発が完結」だが、**AIを信頼して使える仕組みがない**
- 根本原因は **評価・検証の仕組みが不在** であること。これがAI活用の最大のボトルネック
- 3つの理由:
  1. 人による評価がスピードを殺している
  2. ベストプラクティスが世の中にまだない
  3. 再現性の追求(属人性を排除し、誰がやっても同じ品質を出したい)

**エレベーターピッチ(7/10時点)**

> AI駆動開発で生成される成果物について、再現性・正確性・信頼性を確保する仕組みを構築する。
> CCSHやハーネス活用等を参考に、品質保証手法の確立を目指す。

### 1.3 想定読者(倒したい相手)

7/23の議論で具体化された、この研究が説得すべき相手:

- 「AI駆動開発は早く・安くなる分、**品質は悪くなるんでしょう**」と疑う層
- 技術判定を行う部長・本部長クラス
- 品質保証部門(「大丈夫」と言えるかどうかを判断する立場)
- 契約上「テストは全部この手順でやること」と縛られている現場

※ 一方で「品質さえ下がらなければよい/むしろ上がるならよい」と上層部から言われているケースもあり、
全社が反対しているわけではない、という認識も共有された。

7/10の集中検討会で決定した4分科会構成と、全体ストーリー
「① 基盤を整える → ② AIと協調して開発する → ③ 生成物を評価・信頼する → ④ 継続的に改善する」。

| 分科会 | テーマ | 担当領域 |
|---|---|---|
| 第1 | AI-Ready基盤 | データ基盤、コンテキスト設計指針、AI-Readyガイドライン |
| 第2 | AI駆動開発 | 開発プロセスの**ループ構造**、人とAIの役割分担モデル、AIエージェント活用パターン |
| **第3** | **AI品質保証** | **ハーネス(CLAUDE.md / Skills 等)による品質担保、評価指標、レビュー基準** |

### 2.1 第2分科会との境界(7/23議論)

最も曖昧になりやすい箇所。現時点の整理:

- **ループ構造で開発を回すこと自体** = 第2分科会
- **どういう条件でループが機能するか(品質が収束する条件)** = 第3分科会
- テストのやり方・評価方法の概論 = 第2分科会と重複しうるため、第3分科会は
  **より深掘りした「ハーネスで品質を高める部分」** を取る

→ **要すり合わせ**。主査・副主査間で「やる/やらない」を整理した上で、部会全体でダブりなく確認する段取り。

### 2.2 第1分科会との境界(7/23議論)

- **実データの管理方法・データの持ち方そのもの** = 第1分科会
- **AIがそのデータへ「どう制御されてアクセスするか」** = 第3分科会

→ こちらも明文化が必要。

## 3. 研究の全体設計(5ステップ)

7/23の議論を踏まえて構成した研究フロー。
**ステップ2を「前提」ではなく「仮説」として置く**ことで、調査結果がどちらに転んでも成立する構造にしている。

> **前提: 評価対象 = 開発プロセス全体**(7/23決定)
> コード単体や特定成果物に絞らず、要件定義〜リリース判定までのプロセス全体を対象とする。
> 「バグの原因は実装・設計・要件のどこにでもあるため、テストフェーズだけの問題にしない」という議論に基づく。

```
[1] 各社の品質基準を持ち寄る
      ↓  適用課題の言語化
[2] 仮説: 素のワークフローでは各社の品質要件を満たせない
      ↓  検証
[3] ギャップの特定(何が満たせて、何が満たせないか)
      ↓  設計
[4] ドメイン知識・品質基準をハーネスに落とし込む
      ↓  測定
[5] 効果測定 → 品質保証部門も納得できる提言としてまとめる
```

### ステップ1: 各社の品質基準の収集とカテゴリ化

- AI駆動開発の実施有無に関わらず、**各社が「今」何をもって品質OKと判断しているか** を持ち寄る
  - 例: リリース判定基準、テスト密度、バグ収束曲線、レビュー基準、品質保証部門の承認プロセス
- これを整理し、**「AI駆動開発の適用を阻む要件」= 適用課題** としてカテゴリ化する
- ⚠️ この段階で「**その基準は測定可能か**」を意識しておくこと(ステップ5の効果測定に直結するため)

**成果物**: 各社品質基準の比較レポート / 適用課題カテゴリ一覧

### ステップ2: 仮説の設定

> **仮説**: 汎用的なAI駆動開発ワークフロー(AI-DLC v2 等を代表例として)の素の状態では、
> 各社が要求する品質基準・リリース判定基準は満たせない。

- 特定ベンダーの型を前提にしないため、**AI-DLCは「代表例」として扱い、結論は特定ツール非依存の形で書く**
- 世の中には類似のフレームワークが複数存在するため(§5参照)、横並びで共通項を抽出する

### ステップ3: 仮説の検証(ギャップ特定)

- 素のワークフローで **何が満たせて、何が満たせないか** を切り分ける
- 満たせない部分 = ハーネスでカバーすべき領域

### ステップ4: ハーネス設計

- 各社のドメイン知識・品質基準を、どうハーネスに落とし込むかを設計
  - **ガイド系**(事前): CLAUDE.md、Skills、コーディング規約、設計指針
  - **センサー系**(事後): テスト、リンタ、静的解析、AIレビュー、人によるレビュー
- 「どんなハーネスが必要か」を体系化する

### ステップ5: 効果測定と提言

- ハーネス適用の有無で品質がどう変わるかを測定
- 最終アウトプットは資料ではなく **「品質保証部門・技術判定層が納得できる材料」**

### 中間報告 / 最終報告の線引き(案)

| | 到達目標 |
|---|---|
| **中間報告(10/2)** | ステップ1〜3(適用課題の言語化 + 仮説検証によるギャップ特定) |
| **最終報告(2027/3)** | ステップ4〜5(ハーネス設計 + 効果測定 + 提言) |

→ この線引きを明示しておくことで、中間報告時に「途中で終わっている」ではなく「計画通り」と言える。

## 4. やること / やらないこと / あとで決めること

> **7/23 部会全体発表版**。分科会内の議論を整理し、全体に向けて発表した確定版。

### 4.1 やること

- 品質に直結するハーネスを軸にする(ハーネス全般ではなく品質保証に直結する部分にフォーカス)
- 大企業がAI駆動開発を導入する際に持つ品質面の懸念・抵抗(早く安くなる分品質が落ちるのでは、という疑念)を洗い出し、**ギャップを整理する**
- 世の中の事例に対して**品質がどう変わったのか**を整理する
- 各社の今の品質評価(リリース時のクライテリア)のやり方をまず洗い出す(AIを使っているかどうかに関わらず)
- 事例調査は紹介で終わらせず、**CC研企業への示唆・提言まで昇華**させる
- 検証に使うツール(Claude Code等)を絞ったメンバーで試す方向で選定する(**次回=第3金曜までに決定**)
- **第1分科会との境界線のすり合わせ**(主にコンテキスト)
- **第2分科会との境界線のすり合わせ**(主にループ構造)
- **評価対象の最終決定 → 開発プロセス全体**
- やらないこと含めた全体感の整理(以下、安全側のガードレール的な話の部分など)

**補足: 分科会内議論で確認された方針・スタンス**(発表版には明記されていないが背景として保持)

- 「やる/やらない」を並べる前に、**何を発表したいか・何を試すのか(仮説)** を先に明確化する。仮説なしに手を動かさない
- ハーネスは「唯一の正解」ではなく **「知識の一つ」** として扱う(登場して間もない概念であり将来陳腐化しうるため、時点をピン留めした上で活用する)
- 技術課題だけでなく **適用課題**(JTC・大企業に当てはめたとき何がハードルになるか)まで踏み込む
- 古い品質指標を全否定しない。「ここは従来通りでOK、ここは考え方を変えませんか」という提案スタイルを取る
- ベストプラクティスを「どこに・どう当てるか」を体系化する
- アンチ寄りの層(品質を心配する部長クラス等)へのインタビュー/ヒアリングを検討する

### 4.2 やらないこと

- **特定ベンダー(AWS AI-DLC等)のワークフレームワーク・エージェント構成をそのまま自分たちの型として採用・推奨すること**
- **品質に直結しない、安全側のガードレール的な話**(例: AIが誤ってDBを破壊しない、といった話)
- **実データの管理方法・データの持ち方そのもの**(第1分科会の領域。AIがそのデータにどう制御してアクセスするかは第3分科会側)
- **LLM自体の性能比較**
- **人・組織の品質評価能力**(リテラシースキル不足、レビュー人材の役割)

**補足: 分科会内議論で挙がったが発表版では上記に集約された項目**

- ハーネスをゼロから作り込むこと(既存ベストプラクティスへの適用課題を考える方向)
- 開発プロセスのループ構造そのものの設計(第2分科会の領域 → 「第2分科会との境界線すり合わせ」に統合)
- テストのやり方・評価方法の詳細設計(同上)
- セキュリティ研究領域(7/10からの継続合意)

### 4.3 あとで決めること

**7/23 発表版で明示されたもの**

- 実際に開発してみる(PoC)を行うか、その規模感(仮説が固まってから判断)
- ツール利用費用の算出・企画委員会への申請(ツール確定後)
- 複数人でのツールアカウント共有の可否、公平性の担保方法
- ハーネスという言葉自体への依存度(新しい概念のため、唯一の正解ではなく知識の一つとして位置づけるか)
- **品質を再現性・正確性・責任の3軸に分解して具体化する**(前回OSTの整理を踏襲)

## 5. 参考: 世の中の類似ワークフレームワーク

「AI-DLCのようなワークフロー」は既に複数存在し、**仕様駆動開発(Spec-Driven Development, SDD)** というカテゴリで括られている。
特定ベンダー依存を避けるため、複数を横並びで比較し共通項を抽出する方針を取る。

| 名称 | 提供元 | 特徴 |
|---|---|---|
| AI-DLC | AWS | ライフサイクル全体のフェーズ分割が主軸。Kiro / Amazon Q Developer / Cursor / Cline / Claude Code / GitHub Copilot / OpenAI Codex 等に対応 |
| Spec Kit | GitHub | OSSのSDD実践キット。ワークフロー・テンプレート・CLIを提供 |
| Kiro | AWS | 仕様起点の成果物チェーンが主軸 |
| BMAD / OpenSpec / cc-sdd | 各種OSS | 同上カテゴリ |

**分科会にとって有用な既知の論点**

- AI-DLCとSDDは対立ではなく **並列関係**。どちらも「構造化アプローチ」に属し、主軸の置き方が異なるだけ
- **既に「素のワークフローでは足りない」報告が存在する**
  → AI-DLCではサイクルごとに要件書・設計書・コードが生成されるが、
    「どれが正しい仕様か」はフレームワーク側で定義されていない(＝仮説2の裏付けになりうる一次情報)
- **適用限界も語られている**
  → 「仕様が外部から完全に決まっている受託開発」では、既に詳細な仕様書があるため仕様を再生成する意味が薄い
    (＝大企業・SIer文脈での適用課題そのもの)

## 6. 参考: ハーネスの定義(中島さん調査資料より)

SharePoint「テーマ③品質保証 / ハーネスの定義」に格納された調査資料の要点。

- **Agent = Model + Harness**(Anthropic / Martin Fowler の整理)
- ハーネス = モデルの「外側」の仕組み全部(プロンプト、ツール、実行環境、テスト、レビュー、監視 等)
- 事前の **ガイド**(規約・設計書)と事後の **センサー**(テスト・リンタ・AIレビュー)の両輪
- AWS AI-DLC v2 の用語集に「ハーネス」が正式登場。単一ツールに依存しない **マルチハーネス** 構成を採用
- Databricksの実証: **ハーネス改善だけで正答率 36.1% → 52.6%** に向上
- METR 2025 RCT: 熟練OSS開発者がAIツール使用時、**実測では作業時間が19%増加**したが、本人は「20%速くなった」と体感
  → **体感と実態のギャップ** こそが品質保証を必要とする根拠
- AIに書かせるほどレビューできる人が失われる **パラドックス**(統制・精通知識・自己投資の喪失)
- HITL(人が都度承認)→ HOTL(AIが自律実行、人は監視のみ)への移行が必要だが、
  検知の仕組みがないHOTLは **「統治の演技」** に陥る

### 8.1 中間報告書のフォーマット制約(8/6配布資料より。2026-08-05追記)

#### 8.1.1 成果物フォーマット: 中間報告書の構成とシナリオ(線)設計

> 中間報告資料は、単に4つの分科会の進捗を「点」として並べるのではなく、
> それらが **「一本の線(シナリオ)」** でつながっているストーリーを描く必要がある。

**基本構成(推奨)**

| # | 項目 | 担当 |
|---|---|---|
| ① | 研究会の目的と背景 | **共通パート** |
| ② | 4つの分科会の編成と切り口の根拠 | **共通パート** |
| ③ | 分科会を「線」でつなぐストーリー(全体シナリオ) | **共通パート** |
| ④ | **各分科会の仮説と検証計画(As-Is/To-Be)** | **各分科会**(2スライド程度) |
| ⑤ | 今後の活動スケジュールと深堀り計画(下期の検証ロードマップ) | **共通パート** |

**④の記載内容(← 第3分科会が注力する部分)**

- 各分科会が定義した「**理想形(To-Be)**」の仮説
- それに対する**現実(As-Is)の課題**
- **PoCやヒアリングを通じた検証の進め方**
- ※ 各分科会ごとに **2スライド程度**で簡潔にまとめる

**作成・提出フロー**

- ①②③⑤ は部会全体で統一された **共通パート**
- 各分科会は ④ の作成に注力し、**共通パートに必要な情報や意見のエッセンスを取りまとめ担当者へ提出する**

**③ 全体シナリオにおける第3分科会の位置**

> 「あるテーマで定義された仕様(インプット)が別のテーマの開発プロセスで処理され、
> **そこで得られたシステムがまた別のテーマのテスト・品質保証に渡り**、
> 最終的な運用での成果が再び上流にフィードバックされる」

→ 第1(仕様・コンテキスト) → 第2(開発プロセス) → **第3(テスト・品質保証)** → 第4(運用) → 上流へ還流、という並びが想定されている。

#### 8.1.2 雛型ファイルの制約

**全体の目次(固定)**

1. 研究の背景 / 2. 研究の目的 / 3. 体制 / 4. 活動実績(4-1 AI-Ready基盤・4-2 AI駆動開発・**4-3 AI品質保証**・4-4 xxxx) / 5. 今後の活動方針

**分科会の持ち分**

| 項目 | 分量 |
|---|---|
| 3. 体制 | 分科会名・氏名・会社名 |
| **4-3. 背景・目的** | **2ページ程度**(活動の目的(ゴール)、課題、研究の進め方を記載) |
| 5. 今後の活動計画 | ガントチャートに**1行程度の幅** |
| Appendix | 本編に収まらないものを掲載。**インセプションデッキの結果**をここに置く。フォーマットは各分科会で自由(色味・レイアウトは本編に揃える) |
