01
一言でいうと

AI-DLCという考え方 / aidlc-workflowsという実装 / 2.0という世代

工程と承認を持ち込む方法論
$ ターミナル/aidlc 在庫管理の REST API を作りたい

これだけで、要求の整理 → 実現性の検討 → 要件定義 → アーキテクチャ設計 → 作業単位への分解 → 実装 → テスト → デプロイ までを決められた順番のステージとして進行させる。各ステージの終わりには必ず人間の承認ゲートがあり、承認しない限り次に進まない。生成された成果物と、そこに至った判断はすべてファイルとして残る。

02
なぜこれが要るのか

アドホックなAIコーディングが本気のプロジェクトで破綻する3つの理由

アドホックな AI コーディング（「このアプリ作って」と投げる）は小さいうちはよく動く。破綻するのはプロジェクトが本気になってから。3つが起きる。

1
コンテキストが流れる
プロンプトをまたぐうちに最初に合意した前提が薄れる。会話が長くなるほど初期の決定は「なかったこと」になりやすい
2
判断の根拠が残らない
なぜその設計にしたのかがチャットログに埋もれる。3週間後に読み返せる形になっていない
3
頼んでいないことをやる
気づいたら別のファイルが書き換わっている。どこで方針が変わったか後から特定できない
AI-DLC の答え：工程に構造を入れる。 ステージごとに担当（エージェント）が決まり、次に進む前に必ず承認ゲートを通り、やり取りの結果はファイルと監査ログに落ちる。加えて人間の訂正を記録して次回以降に引き継ぐ（学習ループ）。

設計原則：同じエンジンで使い捨ての PoC も規制産業向けの本番機能も回せる。違いは「どれだけのステージを、どれだけの深さで走らせるか」だけで、別のツールに乗り換える必要がない。

04

32ステージのうちどれを走らせるか。標準で9種類同梱

バグ修正に市場調査は要らない。規制産業の機能追加でコンプライアンス確認を飛ばすわけにもいかない。スコープが「32のうちどれを走らせるか」を決める。

指定方法：明示指定（/aidlc bugfix ログイン不具合の修正）もできるが、自由文から自動判定もされる。「fix」「bug」なら bugfix、「CVE」「脆弱性」なら security-patch。判定結果は必ず実行前に確認される。

$ 実行前の確認例（そのまま引用）Starting a "bugfix" workflow for: "fix login bug" - 7 of 32 stages, 4 approval gates, 1 stage repeats per unit of work in Construction.

何ステージ走って承認ゲートが何回あるのかを、始める前に必ず数字で提示。コンパイル済みグリッドから計算された実数で推測値ではない。違うと思えば別スコープを指定できる。

ナイキストモデル ＝ テスト戦略 Minimal の呼び名 要件1つにつきテスト1本（＋各コンポーネントに最低1本のハッピーパス）。信号を復元するのに必要な最小サンプリング周波数、という比喩から。

自動提案（composer）：当てはまるスコープがないとき、リッチな文章を投げると既存スコープに無理やり寄せず「専用の計画を組みましょうか？」と composer が提案。タスクの曖昧さ・コードベースの不確実性・検証コスト・リスクを見積もり、必要十分な最小のステージ集合を組み立て、各ステージについて実行/スキップの理由を添えた表を提示。承認するまで何も書き込まれない。

05
誰が働くのか ― 14エージェント

30個の細かい専門エージェントではなく、広い守備範囲のモブ編成

設計原則：AI-DLC は「30個の細かい専門エージェント」を作らない。専門を細かく割るほど引き継ぎの連鎖（＝ウォーターフォール）が復活するから。代わりに広い守備範囲を持つ11のドメインエージェントが複数ステージ・複数フェーズをまたいで働く。3〜5人のモブが機能ひとつを最初から最後まで見る、という人間のチームの形を写したもの。

06
人間はどこで関わるのか

承認ゲートの本物性と、3つの対話モード

ステージ末の承認ゲート（画面そのまま）：

$ 承認ゲート画面▸ How would you like to proceed? (1) Approve — Continue to [次のステージ名] (2) Request Changes — 修正内容を伝える

Initialization の3ステージを除く全ステージにこのゲートがある。「次のステージ名」は推測ではなくエンジンが計算した実際の遷移先。

ステージ完了
Approve
次のステージへ
Request Changes
3周目に入ると「Accept as-is」が出現（2周目で予告）

ゲートの本物性：このゲートは本物の人間の操作を要求する。プロンプトを打つ／選択ウィジェットに答えると監査台帳に「人間のターン」が記録され、前回のゲート解決以降にそれが1件もなければ承認は拒否される。モデルが自動運転のまま「承認されました」と自作自演することを構造的に防ぐ。

3ストライク・エスケープハッチ：同じステージで修正依頼が3周目に入ると「このまま受け入れる（Accept as-is）」が現れる。2周目の時点で「次から出ます」と予告される。エージェントと平行線になったときに無限ループしないための逃げ道。

ステージ中の3つの対話モード。途中でモードを切り替えても進捗は失われない。3つとも質問ファイルという同じ着地点に収束するよう設計されているため。

Guide Me
構造化された質問に答える。抜け漏れが出にくい
Edit File
空欄つきの質問ファイルに自分のペースで書き込む
Chat
自由に議論し、決定事項を質問ファイルに抽出
質問ファイル
3モード共通の着地点
07
成果物はどこに残るのか

エンジン本体（.claude/）と成果物（aidlc/）を分離

実行するとプロジェクト直下に aidlc/ ができ、AI-DLC が作るものはすべてここに入る。エンジン本体（.claude/ 等）とは分離されていて、人間が読む側は aidlc/ だけ見ればいい。

スペース = 1チームの世界
└ インテント = 仕事1件
└ 状態・監査証跡・成果物
$ ディレクトリ構造my-project/ ├── .claude/ エンジン（ツール・フック・スキル・エージェント）※普段は開かない ├── aidlc/ │ └── spaces/ │ └── default/ ← 「スペース」＝ 1チームの世界 │ ├── memory/ 方法（org.md / team.md / project.md / phases/） │ ├── knowledge/ ドメイン知識（自分たちで足す） │ ├── codekb/ コードベースの知識 │ └── intents/ ← 「インテント」＝ 1つの仕事 │ ├── 260620-inventory-api/ 完了した仕事 │ └── 260624-export-bug/ 進行中の仕事 │ ├── aidlc-state.md 今どのステージにいるか │ ├── audit/ 決定の証跡 │ └── inception/requirements-analysis/requirements.md └── repo-a/ repo-b/ コードのリポジトリは兄弟として置く

覚えるべき概念は2つだけ。インテント ＝ 仕事1件。ライフサイクルの1回分の実行。機能開発の途中で緊急バグが来ても別インテントとして並走でき、元の進捗は一切触られない。スペース ＝ 1チームの世界（方法・知識・仕事の記録一式）。ひとりまたは1チームなら default のまま、存在を意識する必要はない。

git との関わり：aidlc/ は git にコミットする前提。方法も監査証跡も成果物もチームで共有される。例外は「いま自分がどこにいるか」を示すカーソル2つ（active-space / active-intent）で、これはユーザーごとにローカル（gitignore 対象）。同僚と別々のインテントに座れるようにするため。

08
訂正が資産になる ― 学習ループ

日誌 memory.md が承認ゲートで候補提示され、project.md に蓄積

ステージの実行中、フレームワークは裏で日誌（memory.md）をつけている。記録される4種類：

Interpretations

Deviations
意図的に手順から外れた理由
Tradeoffs

Open questions
次回までに確認したいこと

project.md

ワークフローへ

承認ゲートの直前に、この日誌の各行がそのままの文言で候補として提示される（要約も「面白そうなもの」の選別もしない）。加えて「次回のために何か追加することは？」と必ず聞かれる。残したい項目にチェックを入れると memory/project.md にプラクティスとして書き込まれる。

STEP 1〜2 ― 実例（銀行案件）
「リトライで transaction が二重にならないように」
エージェントはこれをデータベーストランザクションと解釈し、ACID の要件として起票した
STEP 3〜4 ― 訂正と定着
「いや、決済のことだ」
担当者が訂正 → ゲートで候補に上がりチェック → project.md に残る → 次回のワークフローから最初のステージで「このプロジェクトの transaction は決済のこと」として動く

一度払ったコストが以降ずっと効き続ける設計。

重要な挙動：ここで記録したルールは実行中のワークフローには反映されない。次回から。 ルールやステージ定義は「ワークフロー開始時に1回だけ」コンパイルされ、実行中は解決済みの結果だけを読む設計（ルーターの経路計算とパケット転送を分けるのと同じ発想）。途中でルールが変わらないので、序盤に承認したゲートの前提が後から書き換わらない。

センサー：ルールが「エージェントが読む散文」なのに対し、センサーはエージェントがファイルを書いた瞬間に自動で走る決定論的なチェック。標準で5本（必須見出しの有無、上流成果物への参照カバレッジ、主張のソースタグ、リンター、型チェック）。現在の版では助言的で、失敗しても承認ゲートを止めない。監査ログに記録され、何が足りないかを指す詳細ファイルが残る。

09
正直なところ、どうなのか

良い面3点、引っかかる面3点

良い面
  • 決定が残る ― 82種類の監査イベントと成果物ファイルで、「なぜこうなったか」がチャットログの外に残る。監査が要る現場では効く
  • 儀式の量を選べる ― 7ステージから32ステージまで同じエンジンで連続的に変えられる。重い方法論にありがちな「全部か無か」ではない
  • カスタマイズがデータ側 ― ステージもエージェントもスコープも Markdown + YAML。TypeScript を書かずに方法論を組み替えられる
引っかかる面
  • ゲートは多い ― feature なら承認29回。Construction は「Bolt」単位でまとめる設計になったが、それでも人間の時間は要る
  • トークンを食う ― 32ステージ×成果物生成。フルスコープを回すコストは相応。ステータスラインにトークン数と概算コストが出るのはそのため
  • モデル依存が強い ― 公式に「Claude Opus 4.8 推奨」。弱いモデルでは指揮役がレビューや学習ループを飛ばしたり、ゲートを急いだりすると明記されている

環境要件：配布物の既定設定は AWS Bedrock 前提（リージョンとモデルIDが固定で入っている）。Bedrock のモデルアクセスと AWS 認証情報がないと起動しない。手元の Claude Code の認証で動かしたい場合は設定から Bedrock 関連の環境変数を外す必要がある。

使用上の注意：公式 README 自身が但し書きしている通り、これは「レビューせずに信じる」ためのものではない。承認ゲートが全ステージにあるのは、まさに人間が読むことを前提にしているから。

2つのハマりどころ。起動場所 ― .claude/ を置いたプロジェクトのルートでハーネスを起動する。別の場所で起動しても /aidlc は出てこない。Bedrock 設定 ― 配布物の .claude/ 内の設定ファイルは AWS Bedrock 前提（リージョンとモデル ID が固定）。Bedrock のモデルアクセスと AWS 認証情報がない場合は起動しない。手元のハーネスの認証をそのまま使いたいなら、gitignore 対象のローカル設定ファイルで env の Bedrock 関連キーを上書き・除去する。

試用の推奨：本番のリポジトリではなく空のディレクトリで始める AI-DLC は自分自身の状態ファイルや監査ログも書き込む。コピー直後に git init してタグを打っておくと git reset --hard <tag> && git clean -fd でいつでも初期状態に戻せる。ついでにフレームワーク自身の書き込みと生成された成果物を git diff で区別して観察できる。

まとめ

5行で振り返る

  • AI-DLC は方法論、aidlc-workflows はその実装。 1本のソースから複数の CLI ハーネス向けに配布物を生成する
  • 5フェーズ32ステージ、14エージェント、全ステージに人間の承認ゲート。 決定はファイルと監査ログに残る
  • スコープが儀式の量を決める。 bugfix は7ステージ、enterprise は32ステージ。開始前に必ず数字で提示される
  • 人間の訂正がルールとして蓄積する。 ただし反映は次のワークフローから（実行中は前提が動かない）
  • カスタマイズはコードではなくデータ。 ステージもスコープもエージェントも Markdown + YAML で組み替えられる
