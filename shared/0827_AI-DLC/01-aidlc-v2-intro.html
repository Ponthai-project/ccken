研究会資料 ／ 第1部

AI-DLC Workflows 2.0 とは何か

AWS Labs が公開している「AI駆動開発のためのライフサイクル実装」を、AI駆動開発に馴染みのないエンジニア向けに解説します。 前提知識は「Claude Code のようなコーディングエージェントを触ったことがある」程度で十分です。

作成 東京海上日動システムズ・中島

対象 一般エンジニア 実装 awslabs/aidlc-workflows 版 v2.5.59（2.0 GA） ライセンス MIT-0

1.一言でいうと

AI-DLC は、AIエージェントによる開発に「工程」と「承認」を持ち込む方法論です。 そして aidlc-workflows は、それを Claude Code などの CLI エージェント上でそのまま動く形にした実装です。

使い方はコマンド1行から始まります。

/aidlc 在庫管理の REST API を作りたい

これだけで、要求の整理 → 実現性の検討 → 要件定義 → アーキテクチャ設計 → 作業単位への分解 → 実装 → テスト → デプロイまでを、 決められた順番のステージとして進行させます。各ステージの終わりには必ず人間の承認ゲートがあり、 承認しない限り次に進みません。生成された成果物と、そこに至った判断はすべてファイルとして残ります。

用語の整理

AI-DLC（方法論）＝ AWS が定義した「AI駆動開発ライフサイクル」という考え方。ブログとメソッド定義論文がある。

aidlc-workflows（実装）＝ その方法論を、スキル・エージェント・フック・CLIツールとして書き下ろした OSS。今回の研究対象はこちら。

2.0 / v2＝ この実装のメジャーバージョン。1本のソース（core/）から Claude Code / Kiro IDE / Kiro CLI / Codex CLI / opencode 向けの配布物を生成する構造になった世代。

2.なぜこれが要るのか

コーディングエージェントに「このアプリ作って」と投げる、いわゆるアドホックな AI コーディングは、 小さいうちはよく動きます。破綻するのはプロジェクトが本気になってからで、だいたい次の3つが起きます。

コンテキストが流れる

プロンプトをまたぐうちに、最初に合意したはずの前提が薄れていく。会話が長くなるほど、初期の決定は「なかったこと」になりやすい。

判断の根拠が残らない

なぜその設計にしたのかがチャットログの中に埋もれる。3週間後に読み返せる形にはなっていない。

頼んでいないことをやる

気づいたら別のファイルが書き換わっている。どこで方針が変わったのかを後から特定できない。

AI-DLC の答えは単純で、工程に構造を入れることです。 ステージごとに担当（エージェント）が決まっていて、次に進む前に必ず承認ゲートを通り、 やり取りの結果はファイルと監査ログに落ちる。加えて、人間が入れた訂正を記録して次回以降に引き継ぐ仕組み（後述の学習ループ）を持ちます。

重要なのは、同じエンジンで使い捨ての PoC も規制産業向けの本番機能も回せるように設計されている点です。 違いは「どれだけのステージを、どれだけの深さで走らせるか」だけで、別のツールに乗り換える必要はありません。

3.全体像 — 5フェーズ32ステージ

ライフサイクルは 5 つのフェーズに分かれ、その中に合計 32 のステージがあります。 フェーズの境目には 検証ゲート があり、成果物同士のトレーサビリティ（要件がストーリーに、ストーリーが作業単位に紐づいているか等）を自動チェックします。

各フェーズで何が起きるか

フェーズ目的代表的なステージ
0. Initialization作業場を用意する。ここだけ承認ゲートなしで、1回のツール呼び出しの中で瞬時に終わるワークスペース作成、既存コードの検出、状態初期化
1. Ideation「そもそも何をやるのか」を固める意図の言語化、市場調査、実現性・制約、スコープ定義、チーム編成、ラフモック、承認と引き継ぎ
2. Inception要件を詳細化し、設計して、作業単位に割るリバースエンジニアリング（既存コードがある場合）、開発プラクティス発見、要件分析、ユーザーストーリー、アプリケーション設計、ユニット生成、デリバリー計画
3. Construction作る。レビュー可能な大きさに切って進める機能設計、非機能要件と設計、インフラ設計、コード生成、ビルド＆テスト、CIパイプライン
4. Operation出して、運用するデプロイパイプライン、環境構築、デプロイ実行、可観測性、インシデント対応、性能検証、フィードバック

なお「32ステージ全部を毎回走らせる」わけではありません。これを制御するのが次のスコープです。

4.スコープ — 儀式の量を決めるダイヤル

バグ修正に市場調査は要りませんし、規制産業の機能追加でコンプライアンス確認を飛ばすわけにもいきません。 そこで スコープが「32のうちどれを走らせるか」を決めます。標準で 9 種類が同梱されています。

スコープ実行ステージ既定の深さ使いどころ
enterprise32 / 32Comprehensive規制対象・監査証跡が要る機能
feature32 / 32Standard通常の新機能（既定のフォールバック）
workshop25 / 32Standardワークショップ・研修（題材は事前決定済み）
mvp22 / 32Standardグリーンフィールドの MVP。運用フェーズは省略
infra13 / 32Standardインフラ変更、CDK/CloudFormation
security-patch10 / 32MinimalCVE 対応
poc8 / 32Minimal実現性の検証、スパイク
refactor8 / 32Minimal挙動を変えないリファクタ
bugfix7 / 32Minimal既知のバグ修正

スコープは明示指定（/aidlc bugfix ログイン不具合の修正）もできますが、 自由文から自動判定もされます。「fix」「bug」なら bugfix、「CVE」「脆弱性」なら security-patch、といった具合です。 判定結果は必ず実行前に、こういう1行で確認されます。 

Starting a "bugfix" workflow for: "fix login bug" - 7 of 32 stages,
4 approval gates, 1 stage repeats per unit of work in Construction.

何ステージ走って承認ゲートが何回あるのかを、始める前に必ず数字で提示する。 これはコンパイル済みのグリッドから計算された実数で、推測値ではありません。ここで違うと思えば別のスコープを指定できます。

深さとテスト戦略は別ダイヤル

スコープが「どのステージを走らせるか」なのに対し、深さ（Depth） は「各ステージの成果物をどれだけ詳しく書くか」、 テスト戦略 は「テストをどれだけ書くか」を独立に制御します。3段階（Minimal / Standard / Comprehensive）で、 どちらも実行中の承認ゲートで変更できます。

テスト戦略の Minimal は「ナイキストモデル」と呼ばれていて、 要件1つにつきテスト1本（＋各コンポーネントに最低1本のハッピーパス）という考え方です。 信号を復元するのに必要な最小サンプリング周波数、という比喩から来ています。

当てはまるスコープがないときは

リッチな文章を投げると、既存スコープに無理やり寄せるのではなく「専用の計画を組みましょうか？」と composer（構成エージェント） が提案してきます。 タスクの曖昧さ・コードベースの不確実性・検証コスト・リスクなどを見積もって、必要十分な最小のステージ集合を組み立て、 各ステージについて実行/スキップの理由を添えた表を提示します。承認するまで何も書き込まれません。

5.誰が働くのか — 14エージェント

AI-DLC は「30個の細かい専門エージェント」を作りません。理由は、専門を細かく割るほど引き継ぎの連鎖（＝ウォーターフォール）が復活するからです。 代わりに、広い守備範囲を持つ11のドメインエージェントが、複数のステージ・複数のフェーズをまたいで働きます。 3〜5人のモブが機能ひとつを最初から最後まで見る、という人間のチームの形を写したものです。

エージェント担当領域
product要求、ユーザーストーリー、スコープ、市場調査
designUX/UI、ワイヤーフレーム、アクセシビリティ
deliveryチーム編成、キャパシティ計画、デリバリー順序
architectアプリケーション設計、ドメインモデル、非機能要件、コンポーネント分解（関与ステージ最多）
aws-platformAWS インフラ、CDK/CloudFormation、コスト最適化
compliance規制・統制要件
devsecopsセキュリティ、脅威モデリング
developerコード生成、既存コードのスキャン
qualityテスト設計、ビルド＆テスト、性能検証
pipeline-deployCI/CD、デプロイ
operations可観測性、インシデント対応、SRE
上記11に加えて、レビュー専任2体（product-lead / architecture-reviewer）と、適応ワークフローの composer で計14体

エージェント同士が勝手に呼び合うことはありません。すべての委譲は指揮役（conductor）が行います。 1つのステージには「リード」が1体いて成果物の責任を持ち、必要に応じて「サポート」が加わります。

サポートの参加の仕方は、ステージが宣言する通信トポロジで決まります。 ほとんど（32のうち28）は inline ＝ 指揮役が自分のコンテキスト内で各ペルソナを被って進める形。 残りの4つだけが、実際に独立したサブエージェントを起動する形（ハブ&スポーク／パイプライン／モブ）になっています。

6.人間はどこで関わるのか

ステージ中：3つの対話モード

ステージが人間の入力を必要とするとき、3つのやり方から選べます。

  • Guide Me — エージェントが構造化された質問を出し、それに答える。抜け漏れが出にくい
  • Edit File — 空欄つきの質問ファイルが作られるので、自分のペースで直接書き込む
  • Chat — 自由に議論して、エージェントが決定事項を抽出して質問ファイルに書き戻す

途中でモードを切り替えても進捗は失われません。3つとも 質問ファイルという同じ着地点に収束するよう設計されているためです。

ステージ末：承認ゲート

▸ How would you like to proceed?
  (1) Approve — Continue to [次のステージ名]
  (2) Request Changes — 修正内容を伝える

Initialization の3ステージを除く全ステージに、このゲートがあります。 「次のステージ名」は推測ではなくエンジンが計算した実際の遷移先です。

面白いのは、このゲートが 本物の人間の操作を要求する ことです。 プロンプトを打つ、あるいは選択ウィジェットに答えると監査台帳に「人間のターン」が記録され、 前回のゲート解決以降にそれが1件もなければ承認は拒否されます。 モデルが自動運転のまま「承認されました」と自作自演することを構造的に防いでいます。

3ストライク・エスケープハッチ

同じステージで修正依頼が3周目に入ると、「このまま受け入れる（Accept as-is）」という選択肢が現れます。 2周目の時点で「次から出ます」と予告されます。エージェントと平行線になったときに無限ループしないための逃げ道です。

7.成果物はどこに残るのか

実行するとプロジェクト直下に aidlc/ ができ、AI-DLC が作るものはすべてここに入ります。 エンジン本体（.claude/ 等）とは分離されていて、人間が読む側は aidlc/ だけ見ればいい構造です。 

my-project/
├── .claude/                    エンジン（ツール・フック・スキル・エージェント）
│                               ※ 普段は開かない
├── aidlc/
│   └── spaces/
│       └── default/            ← 「スペース」＝ 1チームの世界
│           ├── memory/         方法（org.md / team.md / project.md / phases/）
│           ├── knowledge/      ドメイン知識（自分たちで足す）
│           ├── codekb/         コードベースの知識
│           └── intents/        ← 「インテント」＝ 1つの仕事
│               ├── 260620-inventory-api/     ✓ 完了した仕事
│               └── 260624-export-bug/        ◷ 進行中の仕事
│                   ├── aidlc-state.md          今どのステージにいるか
│                   ├── audit/                  決定の証跡
│                   └── inception/requirements-analysis/requirements.md
└── repo-a/  repo-b/            コードのリポジトリは兄弟として置く

覚えるべき概念は2つだけです。

  • インテント＝ 仕事1件。ライフサイクルの1回分の実行。機能開発の途中で緊急バグが来ても、 別インテントとして並走でき、元の進捗は一切触られません
  • スペース＝ 1チームの世界（方法・知識・仕事の記録一式）。 ひとりまたは1チームなら default のまま、存在を意識する必要はありません

aidlc/ は git にコミットする前提です。方法も、監査証跡も、成果物もチームで共有されます。 例外は「いま自分がどこにいるか」を示すカーソル2つ（active-space / active-intent）で、 これはユーザーごとにローカル（gitignore 対象）です。同僚と別々のインテントに座れるようにするためです。

8.訂正が資産になる — 学習ループ

AI-DLC の面白い部分がここです。ステージの実行中、フレームワークは裏で 日誌（memory.md） をつけています。 記録されるのは4種類。

  • Interpretations — 指示が曖昧だったので、エージェントがこう解釈した
  • Deviations — 意図的にステージの手順から外れた、その理由
  • Tradeoffs — 検討した代替案と、それを採らなかった理由
  • Open questions — 次回までに確認したいこと

承認ゲートの直前に、この日誌の各行がそのままの文言で候補として提示されます（要約も「面白そうなもの」の選別もしません）。 加えて「次回のために何か追加することは？」と必ず聞かれます。残したい項目にチェックを入れると、 それが memory/project.md にプラクティスとして書き込まれます。

具体例で言うと——

実例（公式ガイドより）

銀行案件で、担当者が「リトライで transaction が二重にならないように」と書いた。 エージェントはこれをデータベーストランザクションと解釈し、ACID の要件として起票した。担当者が「いや、決済のことだ」と訂正した。

この訂正がゲートで候補として上がり、チェックすると project.md に残る。 次のワークフローからは、最初のステージから「このプロジェクトの transaction は決済のこと」として動く。 一度払ったコストが以降ずっと効き続ける、という設計です。

1点だけ挙動として知っておくべきこと：ここで記録したルールは実行中のワークフローには反映されません。次回からです。 ルールやステージ定義は「ワークフロー開始時に1回だけ」コンパイルされ、実行中は解決済みの結果だけを読む設計になっているためです （ルーターの経路計算とパケット転送を分けるのと同じ発想）。 途中でルールが変わらないので、序盤に承認したゲートの前提が後から書き換わることがありません。

センサー：決定論的なセカンドオピニオン

ルールが「エージェントが読む散文」なのに対し、センサーはエージェントがファイルを書いた瞬間に自動で走る決定論的なチェックです。 標準で5本（必須見出しの有無、上流成果物への参照カバレッジ、主張のソースタグ、リンター、型チェック）。 現在の版では助言的で、失敗しても承認ゲートを止めません。監査ログに記録され、何が足りないかを指す詳細ファイルが残ります。

9.正直なところ、どうなのか

研究会で議論する材料として、良い面と引っかかる面を並べておきます。

✓ 決定が残る

82種類の監査イベントと成果物ファイルで、「なぜこうなったか」がチャットログの外に残る。監査が要る現場では効く。

✓ 儀式の量を選べる

7ステージから32ステージまで、同じエンジンで連続的に変えられる。重い方法論にありがちな「全部か無か」ではない。

✓ カスタマイズがデータ側

ステージもエージェントもスコープも Markdown + YAML。TypeScript を書かずに方法論を組み替えられる（詳細は第2部）。

△ ゲートは多い

feature なら承認29回。Construction は「Bolt」単位でまとめる設計になったが、それでも人間の時間は要る。

△ トークンを食う

32ステージ×成果物生成。フルスコープを回すコストは相応。ステータスラインにトークン数と概算コストが出るのはそのため。

△ モデル依存が強い

公式に「Claude Opus 4.8 推奨」。弱いモデルでは指揮役がレビューや学習ループを飛ばしたり、ゲートを急いだりすると明記されている。

配布物の既定設定は AWS Bedrock 前提（リージョンとモデルIDが固定で入っている）です。 Bedrock のモデルアクセスと AWS 認証情報がないと起動しません。手元の Claude Code の認証で動かしたい場合は、 設定から Bedrock 関連の環境変数を外す必要があります。

もう1点、公式 README 自身が但し書きしている通り、これは「レビューせずに信じる」ためのものではありません。 承認ゲートが全ステージにあるのは、まさに人間が読むことを前提にしているからです。

10.手元で触ってみる

必要なものは bun と、対応するハーネス（Claude Code など）だけです。 フックと CLI ツールが全部 bun で動くので、これが唯一の共通要件になります。 

# bun（Windows PowerShell）
irm bun.sh/install.ps1 | iex

# bun（macOS / Linux）
curl -fsSL https://bun.sh/install | bash

次に、リポジトリを取得して配布物を自分のプロジェクトにコピーします（Claude Code の例）。 aidlc/ は .claude/ の中ではなく兄弟として置くのがポイントで、 これを忘れると --doctor の「workspace shell ready」チェックが落ちます。 

git clone https://github.com/awslabs/aidlc-workflows.git
cd aidlc-workflows && git checkout v2

cp -r dist/claude/.claude/ your-project/.claude/
cp -r dist/claude/aidlc/   your-project/aidlc/

cd your-project && claude

セッションの中で：

コマンドやること
/aidlc --doctorセットアップの健全性チェック（まずこれ）
/aidlc --help全オプション一覧
/aidlc --status進行中ワークフローの状態
/aidlc <やりたいこと>ワークフロー開始（スコープは文面から自動判定）
/aidlc compose "..."タスクに合わせた専用のステージ計画を提案させる
/aidlc intentスペース内のインテント一覧／切り替え
試すなら使い捨てのワークスペースで

AI-DLC は自分自身の状態ファイルや監査ログも書き込むので、本番のリポジトリではなく空のディレクトリで始めるのがおすすめです。 コピー直後に git init してタグを打っておくと、git reset --hard <tag> && git clean -fd でいつでも初期状態に戻せます。 ついでに、フレームワーク自身の書き込みと生成された成果物を git diff で区別して観察できるようになります。

2つのハマりどころ

起動場所 — .claude/ を置いたプロジェクトのルートでハーネスを起動してください。別の場所で起動しても /aidlc は出てきません。

Bedrock 設定 — 配布物の .claude/settings.json は AWS Bedrock 前提（リージョンとモデル ID が固定）です。 Bedrock のモデルアクセスと AWS 認証情報がない場合は起動しません。手元のハーネスの認証をそのまま使いたいなら、 .claude/settings.local.json（gitignore 対象）で env の Bedrock 関連キーを上書き・除去してください。

11.まとめ

この資料の内容を5行にすると：

  1. AI-DLC は方法論、aidlc-workflows はその実装。1本のソースから複数の CLI ハーネス向けに配布物を生成する
  2. 5フェーズ32ステージ、14エージェント、全ステージに人間の承認ゲート。決定はファイルと監査ログに残る
  3. スコープが儀式の量を決める。bugfix は 7 ステージ、enterprise は 32 ステージ。開始前に必ず数字で提示される
  4. 人間の訂正がルールとして蓄積する。ただし反映は次のワークフローから（実行中は前提が動かない）
  5. カスタマイズはコードではなくデータ。ステージもスコープもエージェントも Markdown + YAML で組み替えられる

最後の点、つまり「じゃあ実際どうやって自分たちの方法論に組み替えるのか」が第2部のテーマです。
