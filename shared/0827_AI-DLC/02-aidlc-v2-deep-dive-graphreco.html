01

v2の設計思想：ルーティングをLLMから剥がす

1.x系のSKILL.mdはルーティングロジックの塊だった。v2はここを分割した ── 2.0で最も重要な変更点

1.x系の SKILL.md は、それ自体がルーティングロジックの塊でした。「今どのステージか」「次はどれか」「このスコープではこれを飛ばすか」──を全部プロンプトの散文で書いていたのです。v2はここをengine（決定的コード）とconductor（LLM）に分割しました。

3つの逃がし弁だけが柵（Stopフック）を通り抜けて停止を許される

分担の言い方をすると、engineがルーティングを持ち、conductorが実行品質を持つ。どのステージが次かは決定論的コードが決め、そのステージをうまく走らせる（良い質問をする、判断を人間に見せる）のはLLMの仕事、という切り分けです。

転送ループ

1. directive = bun .claude/tools/aidlc-orchestrate.ts next $ARGUMENTS
2. directive.kind で分岐して実行
3. bun .claude/tools/aidlc-orchestrate.ts report --stage <slug> --result <outcome>
4. directive.kind == done になるまで繰り返す

directiveは aidlc-directive.ts の判別可能ユニオンとして10種類定義されており、そのうち8種類が現在emitされます。残り2つ（dispatch-subagent / present-gate）は将来枠のプレースホルダで、実装してはいけないと明記されています。

kindconductorがやること
run-stageステージ本文を読んで実行し、producesを書き、日誌をつけ、gateフィールドに従ってゲートを出す。ルーティング情報はグラフノードから解決済みで載ってくる
load-steeringルール束を順に適用して保持し、即座に continue <token> を呼ぶ（分割配送のトランスポート）
ask質問を人間に出し、答えを次の report --user-input で返す。engine自身は人間に聞かない
invoke-swarmConstructionの並列バッチをswarmに展開して収束ループを回す
printメッセージ通りに実行。終端型（status/doctor等を出して停止）と継続型（scope変更等のmutationツールを走らせてループに戻る）の2形がある
errorそのまま出して停止
done完了サマリを出して停止
parked再開方法を伝えて停止
未実装枠（将来のプレースホルダ・実装禁止）：dispatch-subagent, present-gate

directiveは出力前に必ず契約に対して検証され、不正なら「conductorが信じてしまう嘘」を出す代わりに非ゼロ終了します。

このループは「LLMのお行儀」に依存させていません。conductorがターンを終えようとするとStopフック（aidlc-continue-workflow.ts）が走り、next を叩いて未処理のdirectiveがあれば停止をブロックし、directiveを reason フィールドで注入し直します。

設計上の含意

「ルーティングをツールに置く」という決定は、カスタマイズの性質も決めています。書き換えるのはengineが読むデータであって、engineのコードではない。ステージを足す・スコープを定義する・ルールを教える──すべてMarkdown+YAMLで、TypeScriptは一切触りません。この線引き（データ／コード）が、後半のカスタマイズ章の全体を貫きます。

02

one core, many harnesses

方法論の本体はハーネス中立な core/ に1回だけ存在し、各CLI向け配布物はそこから生成される

ディレクトリ構成

aidlc-workflows/
│  ── 手書きソース（ここを編集する）──
├── core/                    ハーネス中立な単一の正本
│   ├── tools/                 aidlc-*.ts エンジンツール群
│   ├── aidlc-common/          ステージプロトコル + 32ステージ + conductor.md
│   ├── agents/                14エージェント
│   ├── knowledge/ memory/ scopes/ sensors/ hooks/
│   └── skills/ templates/
│       ※ 散文中のハーネスディレクトリは {{HARNESS_DIR}} トークンで書く
│
├── harness/                 CLIごとの薄い表層（意図的に発散させる部分）
│   ├── claude/  kiro/  kiro-ide/  codex/  opencode/
│   │   manifest.ts ・ orchestrator skill ・ settings ・ onboarding
│
├── plugins/                 任意・所有権つきのAIDLCプラグイン
│
├── scripts/package.ts       ビルド入口。--check が全体のドリフトガード
│
│  ── 生成物・コミット対象・ドリフト監視下（手で触るとCI落ち）──
└── dist/
    ├── claude/.claude/        Claude Codeユーザーがコピーするもの
    ├── kiro/ kiro-ide/ codex/ opencode/
    └── plugins/<name>/<harness>/

編集フロー

# 1. core/ を編集（dist/ は絶対に触らない）
$EDITOR core/aidlc-common/stages/inception/my-stage.md

# 2. 全ハーネスツリーを再生成
bun scripts/package.ts

# 3. ドリフトがないことを確認（CIと同じガード）
bun scripts/package.ts --check

core/ はAI-DLCが「何であるか」、harness/ は各ハーネスが「どう喋るか」、dist/ はユーザーが「何をコピーするか」。編集するのは最初の2つだけで、3つ目はバイトレベルで一致するよう検査されます。違うのは殻だけなので、「Claude Codeで確立した挙動がCodexでは違う」という事態が構造的に起きにくくなっています。

"harness" という語が3つの意味で使われる

リポジトリを読むときの罠です。harness/（配布表層）、docs/harness-engineering/（カスタマイズ担当者向けガイド）、tests/harness/（テストのヘルパライブラリ）は、互いに無関係です。

03

3つのプレーンとコンパイル境界

AI-DLCはネットワーク機器の設計を明示的に借りている。この比喩を掴んでおくと後述の挙動が全部説明できる

プレーン中身ネットワークでいうと
Control plane何が走るべきかのスキーマ。ステージ定義、ルール、センサー経路計算。1回しか走らないので、遅くて賢くてよい
Data plane実際の実行。ステージ実行、エージェント起動、記録ディレクトリのファイルパケット転送。速く、繰り返し、ルックアップで
Management plane観測と設定。--doctor、監査ログ、CLAUDE.md人間のペースで触る面

control planeは開始時に1回だけコンパイル。以降data planeは解決済みの答えを読むだけ

ここから直接導かれる仕様が、「ゲートで記録した学びは実行中のワークフローには効かず、次回から効く」です。BGPが飛行中のパケットのために経路を再計算しないのと同じ理由で、AI-DLCはワークフローの途中で再コンパイルしません。見返りは再現性と、リスタート後のクリーンな復旧です。序盤に承認したゲートの前提が、後から書き換わることはありません。

カスタマイズ時の実務的な意味

ルールやステージを編集したら、効果を見るには新しいワークフローを開始する必要があるということです。ハーネスによってはスキル・エージェント・ルールをセッション開始時にロードするので、dist/ を入れ替えた場合はセッションごと再起動してください。公式トラブルシューティングにも「新しいセッションを開始せよ」と書かれています。

04

ステージファイルの解剖

ステージはワークフローグラフのノードであり、カスタマイズの原子。core/aidlc-common/stages/<phase>/<slug>.md の1ファイル

読者は2人いて、決して重ならない ── frontmatterを変えたらグラフを変えた、本文を変えたら仕事の中身を変えた

なぜ1ファイルに同居させるかというと、レビュアーが「何をproduceするか」と「それを作る手順」を同時に見られるからです。YAMLとプロースを別ファイルに割ると、この可読性が失われます。ステージがレビュー可能であることを、設計上の性質として守っているわけです。

フィールド決めること判断のポイント
requires_stage依存と順序のエッジ本当に他ステージの出力を消費するのか、それとも単に「後に走ればよい」だけか。後者も表示順エッジとして明示的に書く（アルファベット順のタイブレークに任せない）

produces書く成果物（前方エッジ）他ステージが「この成果物を作るのは誰？」と聞いたときの答えになる

mode通信トポロジ誰が参加するかはsupport_agents、どう参加するかがmode
for_each反復するかインスタンスごとに1回走らせる成果物名。Constructionの5ステージがfor_each: unit-of-workを宣言。集約はグラフから推論され、宣言しない
scopesどのスコープで走るかこれを書かないとどこでもSKIP。ステージの存在と実行は別の関門

mode（トポロジ）の4種

mode意味採用ステージ
inlineconductor自身のコンテキストで走る。サポートは「被るペルソナ」として同居28ステージ
subagentハブ&スポーク。リードを新鮮なコンテキストに委譲し、サポートは互いに盲目なスポークとして起動2（practices-discovery, code-generation）
pipelineチェーン。サポートを宣言順に連結し、各リンクは上流の成果を全部見る1（reverse-engineeringの2リンク）

pipelineとmobはsupport_agentsが非空であることを要求します。どのトポロジでも委譲は必ずconductorが行い、エージェント同士は呼び合いません。

重要な境界

ステージファイルは形がイミュータブルなフレームワーク成果物です。ワークフローが本文の3コンパートメント構造を書き換えることはありません。実行中に許されている唯一の書き込みは、学習ループがfrontmatterのsensors:に新しいセンサーIDを追記することだけです。それ以外の変更は、カスタマイズ担当者が意図的に行うものです。

05

グラフのコンパイル

依存グラフはどこにも直接書かれていない。全ステージのconsumes/produces宣言から創発する

グラフは書くものではなく、ステージ宣言から計算されるもの。JSONはビルド成果物であってソースではない

コンパイル時に自動で検証されること

  • グラフ配置：エッジ解決、トポロジカル順序、生産者／消費者ルックアップ、循環検出
  • frontmatterのフィールド検証：lead_agent/support_agentsはloadAgents()で実ファイルに照合。タイポは「実行時に404する不正なグラフ」ではなくコンパイル失敗になる
  • 命名規則：ファイル名のstemとslugの不一致、slugの重複はハードエラー。センサーのID不一致も同様
  • フェーズルールの接続：ステージはディレクトリでフェーズを宣言しているので、対応するphases/<phase>.mdが自動で接続される
  • ドリフトガード：compile --checkはクリーンなら0、YAMLを編集してJSONを再生成し忘れていれば1

自分で確認しないといけないこと

  • スコープ参加：コンパイラはグラフに置くだけで、どのスコープで走るかは決めない。scopes:を書くまで、グラフに存在するがどこでも走らない
  • 本文とエッジの整合：パーサはエッジしか見ない。「◯◯を読め」と本文に書いたなら、その生産元がrequires_stageに入っている必要がある。手で同期する
  • 上流不在時の挙動：required: trueのconsumeは、生産元を飛ばすスコープでは無効化される。仕様でありバグではないが、本文がその不在を優雅に扱うかは書いた人の責任
  • ドキュメント：ステージ数など手書きで列挙している表があるので、同じ変更の中で更新する（Documentation Policy）

グラフの検査コマンド

# トポロジカル順序（追加したslugが出るか）
bun .claude/tools/aidlc-graph.ts topo

# この成果物を作る／読むのは誰か
bun .claude/tools/aidlc-graph.ts producers <artifact>
bun .claude/tools/aidlc-graph.ts consumers <artifact>

# あるスコープの経路上にいるステージ
bun .claude/tools/aidlc-graph.ts scope <scope-name>

# そのスコープの依存が破綻していないか
bun .claude/tools/aidlc-graph.ts validate-scope <scope-name>

カスタマイズの入口（全体地図）

公式ドキュメントは読者を3つに分ける。この区別が「どこまでならコードを書かずに済むか」の地図になっている

ガイドあなたは…変えるのは…
User GuideAI-DLCを使ってソフトを作る何も変えない。/aidlcを打ち、ゲートで答え、成果物をレビューする
Harness Engineer GuideAI-DLCの振る舞いをチームに合わせるフレームワークが読むデータ：ステージ、エージェント、スコープ、ルール、センサー、知識NO CODE
Developer ReferenceAI-DLC自体を変えるそのデータを読むコード：orchestrator、フック、CLIツール、コンパイルパイプライン、テストCODE

境界の判定は単純です。YAML frontmatterつきのMarkdownかJSON設定なら、データ側。.tsを開いた瞬間にコード側。「ステージ追加」「エージェント追加」「スコープ定義」がTypeScript不要であることは、フレームワークの設計原則として明言されています。

入口の一覧

やりたいこと書く場所効き方

1行だけ性質が違うのがチーム知識です。これはcore/の一部ではなく、プロジェクト内・実行時のディレクトリにあり、フレームワークが上書きすることはありません。他はすべてフレームワークのソースとしてcore/に書きます。
07

レシピ：ステージ／エージェント／スコープ

3つの拡張ポイントを、手順とファイルの実物で辿る

A. ステージを1つ足す

そもそも新ステージが要るかを先に問うこと。既存ステージがやっていない成果物をproduceする、あるいは既存がカバーしない形でconsumeする場合に限って正当化されます。「手順の文言を変えたい」「リードエージェントを差し替えたい」「センサーを付けたい」だけなら、既存ファイルをその場で編集すれば十分です。

1
フェーズを決める
ディレクトリがフェーズであり、これは飾りではない。コンパイル時にどのphases/<phase>.mdルール層が接続されるかを決める
2
ファイルを作る
ファイル名のstemがslugであり、slugはエッジ・ジャンプ・監査ログ・スコープ表のすべてで同一性になる。後から改名すると波及するので慎重に
3
エッジを配線する
requires_stage / consumes / producesの3つが互いに整合していれば、コンパイラが自動で位置を決める
4
再生成する
bun scripts/package.ts（インストール済みツリーで反復するならbun .claude/tools/aidlc-graph.ts compile）
5
どのスコープで走るか決める
scopes:に書いて再コンパイル。書くまでは走らない

ここがv2の拡張性契約の核心です──ステージを足すとは、ステージファイルを1つ書くこと。それ以外に構造上必要なものはありません。コンパイルが通れば、その時点で単体実行できます。 

bun .claude/tools/aidlc-orchestrate.ts next --stage <your-slug> --single

--singleは意図的に隔離されていて、メインワークフローのCurrent Stageを絶対に動かしません。進行中のワークフローを単体実行で脱線させることは起こり得ない設計です。

runnerスキルは任意の砂糖

出荷されている各ステージにはskills/aidlc-<slug>/SKILL.mdという薄いrunnerがあり、/aidlc-application-designのように打てます。これは--singleフラグのopt-inなラッパー（6行程度のシェル）で、手書きではなくジェネレータが出力します。だからrunnerの集合とステージの集合が手作業でズレることがありません。 

bun .claude/tools/aidlc-runner-gen.ts write   # 再生成
bun .claude/tools/aidlc-runner-gen.ts check   # ドリフトガード（不一致ならexit 1）

runnerにhooks:ブロックはありません。決定論的スパイン（監査・センサー・グラフ再構築・状態検証）はsettings.jsonにプロジェクト全体で登録されているので、全runnerがタダで継承します。

B. エージェントを足す

core/agents/<slug>.mdにファイルを置くだけです。ハードコードされたエージェント列挙は存在しません──ステージのlead_agent / support_agentsはloadAgents()で実ファイルに照合されます。

ステージとエージェントの関係は非対称です。ステージはリードエージェントを名指しするが、エージェントは自分のステージを名指ししない。これは意図的で、作業の割り当てを変える（ステージを編集）ことと働き手を増やす（エージェントファイルを置く）ことを独立にできます。エージェントを足しても、どこかのステージが使うと決めるまでワークフローは何も変わりません。

モデルとeffortのtier

judgment

セッションのモデルとeffortをそのまま継承。選んだものより下げられることはない。architect・product・design・developer・quality・devsecops・compliance・aws-platformの8体

balanced

judgmentとtemplatedの中間に位置づく標準tier

templated

中型モデル＋低effort（Kiro以外）。delivery・pipeline-deploy・operationsの3体。出力が計画・CI/CD YAML・ランブックの雛形に偏っているため

1体だけ変えたいなら、インストール済みの.claude/agents/aidlc-*-agent.mdのfrontmatterを直接編集（例：model: opus）。ただしdist/を再コピーすると消えます。全体を上限で縛るならcore/memory/のtier_cap:か、パッケージャの環境変数AIDLC_TIER_CAP──どちらもパック時のノブで実行時設定ではありません。

やってはいけないこと

出荷済み14エージェントのファイルに自社の知識を書き足さないでください。フレームワークファイルなのでアップグレードで上書きされます。自社標準はスペースレベルのaidlc/knowledge/<agent-name>/に置く。新しいエージェントを足すのは自由で、そのファイルはユーザー所有です。

C. スコープを定義する（hotfix の例）

スコープは2つに分かれて書かれます。この分割自体が要点です──スコープの同一性は自分のファイルに、所属はステージ側に転置して置く。

1. スコープファイル core/scopes/aidlc-hotfix.md

---
name: hotfix
depth: Minimal
keywords: [hotfix, urgent]
description: 緊急の本番パッチ。回帰テストとデプロイだけ
skeleton: off
testStrategy: Minimal      # 省略するとdepthを継承
review_cap: advisory       # ステージのレビュー階級を下げる（上げることはできない）
runner: true                # /aidlc-hotfix を生成させる場合
---

# hotfix scope

なぜこれらのステージを走らせ、なぜ他を飛ばすのかの散文。

2. 所属タグ：走らせたい各ステージのfrontmatterscopes:にhotfixを足す。タグしなければSKIP。Initializationの3ステージは必ず含める（常に走るため）。

3. 再コンパイルと確認

bun .claude/tools/aidlc-graph.ts compile          # scopes: をgridに転置
bun .claude/tools/aidlc-utility.ts scope-table    # SKILL.mdの表を更新
bun .claude/tools/aidlc-graph.ts compile --check  # exit 0 を確認
/aidlc --doctor

keywordsを入れた場合は、その語を含む自由文がfeatureに落ちずに新スコープを検出することを確認します。逆に、composerが自動生成したスコープはkeywords: []で出荷され、一回きりの計画がキーワード検出に混ざらないようになっています。将来の自動検出対象にするかはゲートで明示的に聞かれる質問であって、副作用では起きません。

スコープは/aidlc --scope hotfixでファイルを置いた瞬間から使えます。runner: trueは1語コマンド（/aidlc-hotfix）が欲しいときだけの砂糖です。

08

レシピ：ルール・センサー・知識

「フレームワークに何を教え込むか」の三つの器。ルールは制約、センサーは信号、知識は情報。

A. ルール — 5層の strict-additive チェーン

図8-1　5層 strict-additive チェーン。下の層が上の層を消すのではなく、すべてが同時にコンテキストへ載る。

aidlc/spaces/<active-space>/memory/
├── org.md          フレームワーク + 組織全体の既定
├── team.md         チームが是認したプラクティス
├── project.md      このプロジェクト固有
└── phases/
    ├── ideation.md  inception.md  construction.md  operation.md

ファイル内に scope: フィールドはありません。スコープはファイル名から来ます。 解決順は org → team → project → phase → stage（第5層のステージ別ルールは将来枠）。 モデルは strict-additive——適用対象のルールはすべてエージェントのコンテキストに現れ、実行時に黙って落とされたり上書きされたりしません。 overrides: ブロックも enforcement: キーワードも、v2 にはもう存在しません。

矛盾は「書き込み時」に捕まえる

図8-2　矛盾は実行時ではなく書き込み時に検出する。だからリゾルバに複雑な優先順位ロジックが要らない。

学習ループが書き込む先は「見出し」が決める
ゲートで確定した学びの見出し着地先扱い
Interpretationsproject.mdプラクティスとして着地
Deviationsproject.mdプラクティスとして着地
Tradeoffsproject.mdプラクティスとして着地
Open questions昇格しない調査項目であってルールではない

行き先は利用者が選ぶのではなく見出しが決めます。既定スコープは常に project、「team に昇格」はワンクリックの明示操作。 そして org への昇格経路は存在しません。1プロジェクトの驚きが組織全体のルールになる事故を、経路そのものを断つことで防いでいます。

B. センサー — pull authoring

図8-3　センサーは pull authoring。取り込みの主導権はステージ側にあり、発火判定はファイル形状で絞られる。

出荷センサー発火対象チェック内容
claim-sourcesIntent Capture の出力全主張にソースタグがあるか、登録情報が権威ある入力と一致するか、保持された仮定が明示確認と厳密一致するか
required-sections記録ディレクトリの md 出力必須の H2 見出しが存在するか（汎用の内容形状チェック）
upstream-coverage同上成果物群が、宣言した上流成果物それぞれを slug / wikilink / ディレクトリパスで参照しているか
linter.ts / .js設定済みリンタ（既定 ESLint）のラッパー
type-check.ts / .tsx設定済み型チェッカ（既定 tsc）のラッパー
現行版でセンサー結果は助言的です。失敗しても承認ゲートは止まらず、監査行と「何が欠けているか」を指す詳細ファイル （<record>/.aidlc-sensors/<stage>/...）が残るだけ。シグナルは出す、判断は人間という構えです。 学習ループがセンサーを提案してきた場合の install はアトミックな2書き込み——マニフェストを scaffold し、発火元ステージの import リストに ID を追記する——で、 SENSOR_PROPOSED / RULE_LEARNED の監査行が残るため、黙って install されることはありません。
C. 知識 — 2層構造

Tier 1方法論知識

フレームワーク同梱。.claude/knowledge/<agent>/。AI-DLC のやり方そのもの。触らない。

Tier 2チーム知識

利用者が足す。スペースレベルの aidlc/knowledge/<agent>/。自社標準・命名規約・ドメイン語彙。フレームワークは上書きしない。

ルールと知識の使い分け：ルールは「常にこうせよ」という制約で strict-additive にコンテキストへ載る。知識は「この領域はこうなっている」という情報で、担当エージェントが起動したときにロードされる。 「PII は必ずマスクする」はルール、「弊社の顧客マスタのスキーマはこう」は知識。

この節が示しているのは、設定の複雑さをどこに寄せるかという設計判断です。多くのポリシー機構は「実行時に優先順位を解決する」方向に進み、 その結果 overrides: や enforcement: といったキーワードが増え、最終的に「なぜこのルールが効かなかったのか」が誰にも説明できなくなります。 v2 はその道を選ばず、矛盾の検出をディスクへの書き込み時点に前倒ししました。書き込み前にセクション単位で org.md と突き合わせ、 衝突していればゲートを止めて衝突している org の文をその場で引用する。利用者に返される選択肢は「書き直す」「見送る」「org ルールのオーナーにエスカレーション」の3つだけです。 矛盾したルールがそもそもディスクに存在しないので、実行時は単に5層を連結すれば足り、リゾルバは単純なまま保たれます。 センサー側も同じ思想で、ステージが sensors: で取り込む pull 形式にすることで「どのステージで何が走るか」がステージ定義を読むだけで分かります。 センサー側からステージを名指しできる push 形式だと、ステージ定義を読んでも実際に走るものが分からなくなるためです。 そして結果を助言的に留め、監査行と詳細ファイルだけを残す。判断の主体を人間のゲートに置き続けるという一貫した構えが、ルール・センサー・知識の三つすべてに通っています。

09

プラグイン機構

チーム固有の一式を「core を汚さずに」配る仕組み。全部無効にすれば素の core とバイト同一に戻る。

「チーム固有の一式を配りたい」場合の答えがプラグインです。新しいステージ・エージェント・スコープ・ルール・センサー・知識、 そして既存 core ステージへの追加的な contribution を、独自のディレクトリ／独自のリポジトリにまとめて配布し、ユーザーの install に合成します。

図9-1　プラグインは core の外側から合成される。可逆性（全無効化＝素の core）が機構全体の担保になっている。

保証その1：プラグインは core/ を編集しない
全プラグインを無効にすると、install は素の core とバイト同一に戻る。
保証その2：ファーストパーティとサードパーティは機構的に同一
同じ構造、同じ継ぎ目、同じコンポーザ、同じ保証。違うのは出自だけ。
リファレンス実装 test-pro/ の中身
test-pro/                                       ← リファレンス実装
  .aidlc-plugin/plugin.json                     マニフェスト（宣言的）
  stages/construction/test-pro-integration.md   新規ステージ
  contributions/construction/nfr-requirements.md 既存 core ステージへの追加
  sensors/aidlc-coverage-threshold.md           新規センサー
  tools/aidlc-sensor-coverage-threshold.ts      そのスクリプト
  scopes/test-pro-validation.md                 新規スコープ
  agents/test-pro-metrics-agent.md              新規ペルソナ
  knowledge/test-pro-metrics-agent/methodology.md
命名の規律
  1. プラグインのステージは plugin: フィールドで自分の所属を名乗る。
  2. produces: する成果物は <plugin>- 接頭辞が必須。名前空間の衝突を機構的に潰す。
  3. 合成側はプラグイン同一性を出荷されたホストマニフェストから導出する。中身が自分のパッケージ名を騙ることはできず、不一致は skip されて --doctor に記録される。
  4. number: は表示ヒントに過ぎない。グラフ上の位置は slug ベースの requires_stage エッジで決まり、番号はエンジンが割り当てる。だからプラグインは番号レンジを予約しない。
install 側は bun .claude/tools/aidlc-utility.ts select-plugins <names> で有効化するプラグインを絞れます。 プラグインは足す、install が選ぶ——無効化してもファイルは残り、再有効化できます。
プラグインにすべきか、ただのステージ／ルールにすべきか
選択肢使いどころ特徴
ステージ／エージェント／ルール全員が受け取るフレームワークの恒久的な一部にしたいときcore 側に置く。誰も opt-in しなくても届く
プラグイン任意で所有権のあるもの。自分のリポジトリで出荷し、opt-in のスコープ（あるいは when: 述語）でのみ起動する「コンプライアンスパック」「テストパック」のようなドメインパック向け

プラグイン機構の価値は「拡張できること」そのものではなく、拡張しても core の同一性が壊れないことにあります。 多くのフレームワークではカスタマイズが core のフォークとして始まり、アップグレードのたびにマージ地獄が発生します。 v2 は「プラグインは core/ を編集しない」を機構的な不変条件として置き、その帰結として 全プラグインを無効にすれば install は素の core とバイト同一に戻るという検証可能な保証を得ました。可逆性があるからこそ、試しに入れてみることの心理的コストが下がります。 もう一つ効いているのがファーストパーティとサードパーティを機構的に同一に扱うという決定です。 公式だけが使える裏口が無いということは、公式自身が同じ制約の下で拡張を書いているということであり、機構の使い勝手が公式の自己都合で歪みにくくなります。 命名の規律も、単なるお作法ではなく合成の安全装置です。produces: の <plugin>- 接頭辞は成果物名の衝突を防ぎ、 プラグイン同一性を出荷されたホストマニフェストから導出する設計は、中身の自己申告を信用しないことで「名前の詐称」を skip と --doctor への記録に落とします。 number: を表示ヒントに留めたのも同じ理屈で、番号レンジの予約という調整コストを発生させないために、位置決定を slug ベースの requires_stage エッジに一本化しています。

10

Construction：Bolt と swarm

v2 で最も試行錯誤の跡が残っている部分。「子守り」と「レビュー不能」の間を三世代かけて詰めた。

Construction の形は、公式ドキュメントが経緯を率直に書いています。ゲートの粒度をめぐる三世代の変遷です。

図10-1　ゲート粒度の三世代。初期＝15ゲート／次＝1ゲート15,000行／現行＝Bolt 単位。

世代やり方問題
初期作業単位ごとにステージ単位で承認3ユニットで15ゲート。「子守り」と言われた
次全ユニットの質問・設計・コード生成を一括、最後に1回レビュー15ユニットだと 15,000 行が1つのゲートに来る。レビュー不能
現行Bolt 単位。1 Bolt ＝ 1ユニット（または依存で束ねた小グループ）に対する 3.1〜3.5 の1周——
ladder prompt — 自律性の選択を1回だけ迫る

図10-2　Bolt の1周、ladder prompt、並列バッチと halt-and-ask。自律モードでも失敗は必ず止まる。

最初の Bolt は walking skeleton——アーキテクチャを端から端まで証明する最小のスライス——で、必ずゲートされます。 それが通った直後に、ワークフロー中ちょうど1回だけこの質問が出ます。 

自律で続行する？ それとも Bolt ごとにゲートする？

答えは aidlc-state.md に Construction Autonomy Mode として記録され、残り全 Bolt を支配し、セッション再開時にも尊重されます。 早い段階での確信チェックポイントと、意図的な自律性の選択を1回だけ迫る設計です。

並列バッチと halt-and-ask
並列バッチ
2つの Bolt が同じ依存前提を共有していて互いに依存しないなら（B も C も A にだけ依存する等）、1つのバッチとして並行実行され、 バッチ末尾の1ゲートが両方をカバーします。conductor は1ターンで複数の Task を発行し、ハーネス組み込みの並列性でコード生成を同時に走らせます。 質問収集と設計成果物生成は Bolt ごとに直列のまま（安いし、質問の答えはどのみち人間を通して直列化されるため）。
halt-and-ask
失敗は自律モードでも必ず止まります。これが自律モードで唯一割り込む場所です。 単独 Bolt の失敗は即停止して retryskipabort を提示。 並列バッチ中に1つだけ失敗した場合は、バッチ全体の完了を待ち、成功した Bolt の成果物をディスクに保全したうえで、 失敗した Bolt についてだけ同じ選択を出します。

三世代の変遷が示しているのは、ゲートの数を減らすことと、ゲートを実用的に保つことは別問題だという発見です。 初期の「作業単位ごとにステージ単位で承認」は 3ユニットで15ゲートを生み、利用者から「子守り」と評されました。 そこで反対側に振り切って全ユニットを一括処理し最後に1回レビューする形にしたところ、15ユニットで 15,000 行が1つのゲートに来るという、 形式上は承認できるが実質的にレビュー不能な状態を招きました。現行の Bolt は、ゲートの単位を「ワークフローのステージ」でも「プロジェクト全体」でもなく、 人間が一度に理解できる作業のまとまりに合わせ直した答えです。 ladder prompt の巧妙さは、自律性の設定を最初に聞かないことにあります。walking skeleton が通るまでは利用者もシステムの出力品質を評価できないので、 「自律で続行するか」という問いに意味のある答えが出せません。1回だけ、それも根拠が揃った直後に聞くことで、選択が惰性でも勘でもなくなります。 そして答えを aidlc-state.md に永続化することで、セッション再開のたびに再確認する煩わしさも消えます。 halt-and-ask が「自律モードで唯一割り込む場所」と明言されているのも重要で、自律の範囲が曖昧なまま運用されると、 結局どこで人間が見ているのか誰にも分からなくなります。並列バッチ中の部分失敗で成功した Bolt の成果物を先にディスクへ保全するのは、 失敗の巻き添えで進捗を捨てないための実務的な配慮です。

11

composer と実行中の再構成

既存スコープに当てはまらない依頼を feature に丸めず、専用計画を組み立てる。実行中でも組み直せる。

既存スコープがどれも当てはまらないとき（キーワードなしのリッチな散文、長い説明の中に埋もれたキーワード）、 /aidlc は黙って feature に落とさず、専用計画の作成を提案します。 

/aidlc compose "デプロイパイプラインを堅牢化し、可観測性を追加する"
/aidlc compose --report sonar.json     # スキャンレポートから構成
/aidlc --new-scope "..."               # 既存スコープに合致しても強制的に custom

図11-1　composer はエントロピーを5成分で見積もり、理由つきの EXECUTE/SKIP グリッドとして提示する。

提示されるのは、各成分の LOW/MED/HIGH バンドと根拠、助言的な合成スコア、そして 全ステージについて EXECUTE と SKIP の理由を書いた表。承認・編集・却下が選べ、明示承認の前に何も書かれず、ワークフローも始まりません。

承認後の挙動は2通り

MATCH の場合

提案が既存スコープに合致していれば、そのスコープでワークフローが誕生する。新しいファイルは作られない。

CUSTOM グリッドの場合

composer が実物のスコープファイル（scopes/aidlc-<name>.md ＋ grid エントリ）を書き起こし、同じターンでそこから誕生する。 以後は普通のスコープと同様に --scope <name> で解決でき、グラフ再コンパイルを生き延びる（compile が合成済みエントリを再生成後のグリッドに畳み戻す）。

実行中の再構成（in-flight recompose）

図11-2　再構成の適用範囲。完了済みと実行中は凍結、Construction 最初の EXECUTE ステージはアンカーとして固定。

  • フリップできるのはカーソルより先の未実行ステージだけ。完了済みと実行中は凍結。
  • strict 検証を通るので、残ステージが必要入力を失うことはない。
  • 決定論的な recompose 動詞を通り、監査ロックの下で RECOMPOSED イベントを残す。
  • Construction の最初の EXECUTE ステージ（walking-skeleton ゲートのアンカー）はフリップできない。
リテラルな動詞は必須ではない。「market research は要らないんじゃない？ この市場は分かってるし」のような普通の会話も、実行中は再構成要求として認識され、 同じゲート・同じ検証・同じ recompose 動詞を通る。

composer が解いているのは「依頼の言葉づかいと、実行すべき工程は別物である」という問題です。 キーワード検出だけに頼ると、キーワードのないリッチな散文や、長い説明の中に埋もれたキーワードを取りこぼし、 結局すべてが汎用の feature スコープに落ちて「全ステージ実行」か「勘で削る」の二択になります。 v2 はここに実装エントロピーの5成分——意図の曖昧さ、コードベースの構造的不確実性、検証エントロピー、リスク、未解決の仮定——という共通の物差しを置き、 各成分の LOW/MED/HIGH バンドと根拠を示したうえで、成果が依存する成果物をすべて生みながら最小で足りる EXECUTE/SKIP グリッドを提案します。 重要なのは合成スコアが助言的に留まり、判断材料としてのみ提示される点、そして明示承認の前には何も書かれない点です。 CUSTOM グリッドが選ばれたとき composer が実物のスコープファイルを書き起こすのも一貫していて、 その場限りの内部状態ではなく通常のスコープと同じ資産になるため、--scope <name> で再利用でき、グラフ再コンパイルも生き延びます。 実行中の再構成では、完了済みステージが実際に解決したことを織り込んでエントロピーを再見積もりするため、各フリップが「なぜ今なら削れるのか」を名指しできます。 そして自然な会話であっても、同じゲート・同じ検証・同じ recompose 動詞を通ることが担保されている。 会話的な入り口を許しつつ、実際の状態変更は決定論的な1本の経路に集約するという構造は、この資料全体を貫く設計方針の典型例です。

決定論的スパイン：フックと監査

17本のフックが骨格を保ち、82種類のイベント型がすべての挙動を観測可能にする。

core/hooks/ に 17本のフックがあり、すべて aidlc-*.ts で bun 実行されます。性質は2つに分かれます。

図12-1　17本のフックの二性質。関所は流れを止められ、記録係は止めずに観測可能性を作る。

種別フック役割
フロー制御系
（止められる）		 aidlc-continue-workflow（Stop）転送ループを決定論的に保証する
aidlc-deliver-stage-rulesステージルールの正確な配送を強制
aidlc-plan-approval-guardコード生成の計画承認を強制
aidlc-state-transition-guard状態の直接遷移を禁止
aidlc-reviewer-scopeレビュアーの読み取り範囲を強制

助言系 write-audit-log, run-sensors, rebuild-stage-graph, validate-state, log-subagent, statusline, record-human-turn, session-start/end, sync-workflow-state, fold-usage 監査発行、センサー配送、グラフ再構築、状態検証、サブエージェント追跡、ステータスライン描画、人間ターン記録、セッションライフサイクル、トークン使用量の畳み込み

監査は 82種類のイベント型で、インテントの audit/ シャードに構造化ログとして書かれます。 STAGE_STARTED / GATE_APPROVED / GATE_REJECTED / RULE_LEARNED / SENSOR_PROPOSED / RECOMPOSED / HUMAN_TURN など、 この資料で説明してきた挙動はすべて監査行として観測可能です。研究会で挙動を追うなら、ここが一番の観測点になります。

承認の偽造防止

図12-2　承認は「前回のゲート解決以降に HUMAN_TURN が記録されているか」で判定される。

人間がプロンプトを打つ／選択ウィジェットに答えると HUMAN_TURN イベントが台帳に記録されます。 承認（および明確化質問への回答）は、前回のゲート解決以降に HUMAN_TURN が1件も記録されていなければ拒否されます。 自動運転のモデルが「承認されました」を自作自演できません。

テストの層
bun tests/run-tests.ts             # 既定：smoke + unit + integration
bun tests/run-tests.ts --ci        # CI と同じ
bun tests/run-tests.ts --release   # + e2e（完全受け入れ）

全 TypeScript で、t*.test.ts の命名。ドキュメントと実装の同期もテストで縛られています。 スコープ×ステージのマトリクス表は tests/unit/t244-scope-matrix-doc-sync.test.ts がコンパイル済みグリッドと突き合わせ、 バージョン・CHANGELOG・README バッジの一致は t68 が縛る。 ドキュメントを「テストされる成果物」として扱っているのは、この手のフレームワークとしては珍しい部類です。

この節は、これまで説明してきた挙動の実装上の裏付けにあたります。フックが2性質に分かれているという点が重要で、 6本のフロー制御系は「止められる」＝守るべき不変条件を機構として強制する関所であり、残る助言系は「止めない」＝観測可能性と付随処理を担う記録係です。 止められる仕掛けを最小限に絞ることで、どこで詰まったのかの診断が容易になります。 HUMAN_TURN による承認の偽造防止は、この設計思想が最も鋭く出た部分です。 自律的に動くエージェントに承認ゲートを設けても、エージェント自身が承認を出力できてしまえばゲートは形骸化します。 v2 は承認の成立条件を「モデルが何を言ったか」ではなく「台帳に人間のターンが記録されているか」という外形的事実に置き換えました。 前回のゲート解決以降に HUMAN_TURN が1件も無ければ承認は拒否される——この判定はモデルの出力から独立しています。 ハーネス差への対処（ウィジェットが記録しない環境では「approve」と打てば記録される、台帳に人間ターンがまだ存在しない環境では fail open）も明記されており、 厳密性と実用性の折り合いが意識的に付けられています。 そして監査の 82種類のイベント型は、単なるログではなく挙動の観測インターフェースです。 評価や検証を行う立場からすると、UI の見え方ではなく監査シャードを読むことが最も確実な理解の経路になります。 最後に、t244 や t68 によってドキュメントと実装の一致がテストで縛られている点は特筆に値します。 ドキュメントが腐らない仕組みを持つフレームワークは、それ自体が長期運用への構えを示しています。

13

落とし穴集

実際に触ると踏みやすい9点。大半は「編集する場所」と「効き始めるタイミング」の誤解に由来する。

図13-1　落とし穴の俯瞰。編集場所・グラフ整合・タイミングの3系統に整理できる。

1dist/ を直接編集

ドリフトガードが CI を落とします。編集は必ず core/（または harness/<name>/）。core/ の編集と再生成した dist/ は同じコミットに入れる。

2scopes: タグ忘れ

ステージを足してコンパイルが通っても、scopes: を書かないとどこでも走りません。「存在させる」と「走らせる」は別の関門。

3実行中の反映を期待する

ルールもステージ定義もワークフロー開始時に1回コンパイル。編集の効果は次回から。dist/ を入れ替えたらセッションごと再起動。

4出荷エージェントに知識を書き足す

アップグレードで消えます。aidlc/knowledge/<agent>/ に置くか、新しいエージェントファイルを作る。

5slug の後付け改名

slug はエッジ・ジャンプ・スコープ表・監査ログ全部で同一性。改名は全方位に波及します。最初に決める。

6本文とエッジの乖離

パーサはエッジしか見ません。「〜を読め」と本文に書いても requires_stage になければ、そこにファイルは無い。手で同期する。

7コンパイラ未実装のキーに手を出す

when: / on_failure: / blocks_on: 等は予約済みだが未実装。スキーマが拒否します。欲しくなった時点でそれはコード変更。

8bun が非対話 PATH にいない

フックとツールは非対話シェルで走ります。ターミナルで which bun が通るのにハーネスが見つけられない場合、export を ~/.zshenv / ~/.bashrc に写す。

9出荷時の設定が AWS 前提になっている

dist/claude/.claude/settings.json は CLAUDE_CODE_USE_BEDROCK=1 / AWS_REGION=us-east-1 と Bedrock のモデル ID を固定しています。 Bedrock のモデルアクセスと AWS 認証情報がないと起動しません。 手元のハーネスの認証をそのまま使いたい場合は、.claude/settings.local.json（gitignore 対象）で env の Bedrock 関連キーを除去します。 AWS_AIDLC_DEFAULT_SCOPE は Bedrock とは無関係なので残して構いません。

同様に .mcp.json は context7（要 API キー）と AWS 系4本（要 uvx ＋ AWS 認証）を宣言しています。 認証のないサーバは単に使えないだけでワークフローは止まらないので、必要になるまで導入しない選択もできます （composer の CodeKB グラウンディングは、MCP がなければワークスペーススキャンにフォールバックする、というのが正常系です）。

9項目を並べて見えてくるのは、踏みやすい落とし穴のほとんどが「機構の境界」の位置に関する誤解だということです。 dist/ と core/ の境界、「存在する」と「走る」の境界、「編集した」と「効き始めた」の境界、対話シェルと非対話シェルの境界。 どれもフレームワークが意図的に引いた線であり、線の存在を知っていれば避けられ、知らなければ確実に踏みます。 とくに 2番の scopes: タグ忘れと 6番の本文とエッジの乖離は、どちらも「書いたのに効かない」型の失敗で、 エラーが出ずに静かに何も起きないため原因究明に時間を取られがちです。パーサはエッジしか見ないという一点を覚えておくだけで、この2つは同時に回避できます。 3番の「実行中の反映を期待する」は、07節までに述べたコンパイル境界の直接の帰結です。再現性を優先した設計の代償が、日常の操作感としてここに現れます。 そして 9番は他の8つと性質が異なり、初回起動そのものを止めるため研究会のような場では最初に当たります。 出荷時の settings.json が Bedrock 前提で固定されている以上、AWS 認証を持たない参加者は .claude/settings.local.json で env の Bedrock 関連キーを除去する手当てを事前に共有しておく必要があります。 逆に .mcp.json 側は認証がなくてもワークフローが止まらない設計になっており、 composer の CodeKB グラウンディングがワークスペーススキャンにフォールバックするのは異常系ではなく正常系である、という切り分けを知っておくと無用な調査を避けられます。

14

研究会向け実験メニュー

易しい順に10項目。触る順序そのものが、構造の理解の順序になるよう組んである。

まず環境を「戻せる」状態にする

本番リポジトリではなく空のワークスペースを用意し、配布物をコピーした直後に git init ＋ タグを打っておくと、 git reset --hard <tag> && git clean -fd でいつでも初期状態に戻せます。 フレームワーク自身の書き込みと生成された成果物を git diff で切り分けられるので、観察目的でもこの形が扱いやすいです。

図14-1　実験10項目を易しい順に。奥に行くほど「見る」から「変える」「評価する」へ移る。

#やること観測ポイント
1bun .claude/tools/aidlc.ts --doctor を Claude Code の外から直接叩くengine が LLM なしで完結していることの確認。ヘルスチェックの項目一覧そのものが機能の索引になっている
2aidlc-orchestrate.ts next の生の出力を見るdirective の JSON 実物。conductor が何を渡されているのか
3/aidlc bugfix <小さな修正> を1周回す7ステージ・4ゲート。git diff でフレームワーク自身の書き込みと成果物を区別して観察できる
4ゲートで意図的に訂正を入れ、学習ループで残すmemory/project.md への着地と RULE_LEARNED 監査行。次のワークフローで効くことも確認
5aidlc-graph.ts scope bugfix と topoグリッドが frontmatter の転置であることの体感
6既存ステージの scopes: に1行足して再コンパイル最小のカスタマイズ。compile --check の落ち方も見ておく
7hotfix スコープを自作するスコープ2分割（identity / membership）の設計意図
8/aidlc compose "..." でリッチな散文を投げるエントロピー5成分の見積もりと、ステージごとの理由つき表
9実行中に「〜は要らないのでは」と普通に話しかける会話が recompose 動詞にルーティングされる様子と RECOMPOSED 監査行
10監査シャードを通して読む82イベント型が、実際に何をどこまで復元できるログなのかの評価
議論したい論点
1. ルーティングを決定論に置く判断は、どこまで一般化できるか 「経路計算はコード、実行品質は LLM」という分割は AI-DLC 固有のものか、それともエージェント設計の一般原則か。
2. コンパイル境界は正しいトレードオフか 実行中は再コンパイルしない。再現性を取って適応性を捨てている。長いワークフローほど代償が大きい。
3. センサーが助言的であること ブロックしないなら、失敗はどこで回収されるのか。ゲートの人間に依存していないか。
4. 32ステージという粒度 スコープで削れるとはいえ、既定のセットは AWS の想定するプロジェクト像に強く紐づいている。自分たちの現場に写すとき、何を捨てて何を足すか。
5. プラグイン機構を使う価値があるのはどの規模から core/ をフォークして直接いじるのと、プラグインとして分離するコストの分岐点はどこか。

この実験メニューは、単なる操作手順ではなく理解の順序を設計したものとして読むべきです。 1〜2 は engine を Claude Code の外から直接叩く項目で、経路計算が LLM なしで完結しているという第1部からの主張を、 利用者自身の手で確かめられるようになっています。--doctor のヘルスチェック項目一覧がそのまま機能の索引になっている点は、 ドキュメントを読むより早く全体像を掴む近道です。 3〜5 は最小のワークフローを1周させ、git diff でフレームワーク自身の書き込みと生成された成果物を切り分ける段階。 だからこそ冒頭の「空のワークスペース＋git init＋タグ」という下準備が効いてきます。 6〜7 は初めて構成を変える段階で、scopes: への1行追加と hotfix スコープの自作を通じて、 スコープが identity と membership に分かれている理由が体感として入ります。compile --check の落ち方をあえて見ておくという指示も実務的です。 8〜10 は評価の段階で、composer にリッチな散文を投げてエントロピー5成分の見積もりを読み、実行中に普通の言葉で話しかけて recompose 動詞へのルーティングを観察し、最後に監査シャードを通読して82イベント型がどこまで挙動を復元できるログなのかを評価します。 提示された5つの論点は、いずれもこのフレームワークが下した明示的なトレードオフに対応しています。 決定論的ルーティングの一般化可能性、再現性と適応性の交換としてのコンパイル境界、助言的センサーにおける失敗の回収先、 32ステージという既定セットの前提、そしてプラグイン分離が割に合う規模の分岐点。 どれも「正解が示されている問い」ではなく、自分たちの現場に写すときに各自が答えを出す必要がある問いとして置かれています。
