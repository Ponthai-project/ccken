1.v2 の設計思想：ルーティングを LLM から剥がす

1.x 系の SKILL.md は、それ自体がルーティングロジックの塊でした。 「今どのステージか」「次はどれか」「このスコープではこれを飛ばす」——を全部プロンプトの散文で書いていたわけです。 v2 はここを分割しました。これが 2.0 でいちばん重要な変更点です。

engine（決定的コード）

aidlc-orchestrate.ts。状態ファイルとコンパイル済みグラフを読み、「次に何をするか」を 1つの型付き directive（JSON） として出力する。サブコマンドは next / continue / report / park の4つだけ。

conductor（LLM）

skills/aidlc/SKILL.md。directive を受け取って実行し、結果を report で返す薄い転送ループ。ルーティングの判断は一切しない。

分担の言い方をすると、engine がルーティングを持ち、conductor が実行品質を持つ。 どのステージが次かは決定論的コードが決め、そのステージをうまく走らせる（良い質問をする、判断を人間に見せる）のは LLM の仕事、という切り分けです。

転送ループ

1. directive = bun .claude/tools/aidlc-orchestrate.ts next $ARGUMENTS
2. directive.kind で分岐して実行
3. bun .claude/tools/aidlc-orchestrate.ts report --stage <slug> --result <outcome>
4. directive.kind == done になるまで繰り返す

directive は aidlc-directive.ts の判別可能ユニオンで、10種類定義されているうち8種類が現在 emit されます （残り2つは将来枠のプレースホルダで、実装してはいけないと明記されています）。

kindconductor がやること
run-stageステージ本文を読んで実行し、produces を書き、日誌をつけ、gate フィールドに従ってゲートを出す。ルーティング情報はグラフノードから解決済みで載ってくる
load-steeringルール束を順に適用して保持し、即座に continue <token> を呼ぶ（分割配送のトランスポート）
ask質問を人間に出し、答えを次の report --user-input で返す。engine 自身は人間に聞かない
invoke-swarmConstruction の並列バッチを swarm に展開して収束ループを回す
printメッセージ通りに実行。終端型（status/doctor 等を出して停止）と継続型（scope 変更等の mutation ツールを走らせてループに戻る）の2形
error / done / parkedそれぞれ、そのまま出して停止／完了サマリを出して停止／再開方法を伝えて停止
未実装枠：dispatch-subagent, present-gate

directive は出力前に必ず契約に対して検証され、不正なら「conductor が信じてしまう嘘」を出す代わりに非ゼロ終了します。

Stop フックがループを保証する

このループは「LLM のお行儀」に依存させていません。conductor がターンを終えようとすると Stop フック（aidlc-continue-workflow.ts）が走り、next を叩いて未処理の directive があれば停止をブロックし、 directive を reason フィールドで注入し直します。

ただし無制限ではなく、いくつもの逃がし弁があります。ここは実装の丁寧さがよく出ている部分です。

  • human-wait カーブアウト：現ステージが承認待ち [?]／修正中 [R]／質問未回答、あるいは直前が単なる雑談だった場合はブロックしない（人間待ちで正しく止まっているため）
  • no-progress カウンタ：進捗のないブロックが上限に達したら手を離す。上限は実行モード依存で、対話時2回・自律 Construction 時8回
  • fail open：アクティブなワークフローがない、あるいは想定外のエラー時は絶対にブロックしない（AI-DLC 以外のセッションを人質にしない）
設計上の含意

「ルーティングをツールに置く」という決定は、カスタマイズの性質も決めています。 あなたが書き換えるのは engine が読むデータであって、engine のコードではない。 ステージを足す・スコープを定義する・ルールを教える——すべて Markdown + YAML で、TypeScript は一切触りません。 この線引き（データ／コード）が、後半のカスタマイズ章の全体を貫きます。

2.one core, many harnesses

v2 のもう1つの柱が配布構造です。方法論の本体はハーネス中立な core/ に1回だけ存在し、 各 CLI 向けの配布物はそこから生成されます。 

aidlc-workflows/
│  ── 手書きソース（ここを編集する）──
├── core/                    ハーネス中立な単一の正本
│   ├── tools/                 aidlc-*.ts エンジンツール群
│   ├── aidlc-common/          ステージプロトコル + 32ステージ + conductor.md
│   ├── agents/                14エージェント
│   ├── knowledge/ memory/ scopes/ sensors/ hooks/
│   └── skills/ templates/
│       ※ 散文中のハーネスディレクトリは {{HARNESS_DIR}} トークンで書く
│
├── harness/                 CLI ごとの薄い表層（意図的に発散させる部分）
│   ├── claude/  kiro/  kiro-ide/  codex/  opencode/
│   │   manifest.ts · orchestrator skill · settings · onboarding
│
├── plugins/                 任意・所有権つきの AIDLC プラグイン
│
├── scripts/package.ts       ビルド入口。--check が全体のドリフトガード
│
│  ── 生成物・コミット対象・ドリフト監視下（手で触るとCI落ち）──
└── dist/
    ├── claude/.claude/        Claude Code ユーザーがコピーするもの
    ├── kiro/ kiro-ide/ codex/ opencode/
    └── plugins/<name>/<harness>/

編集フローは常にこれです。 

# 1. core/ を編集（dist/ は絶対に触らない）
$EDITOR core/aidlc-common/stages/inception/my-stage.md

# 2. 全ハーネスツリーを再生成
bun scripts/package.ts

# 3. ドリフトがないことを確認（CI と同じガード）
bun scripts/package.ts --check

core/ は AI-DLC が「何であるか」、harness/ は各ハーネスが「どう喋るか」、dist/ はユーザーが「何をコピーするか」。 編集するのは最初の2つだけで、3つ目はバイトレベルで一致するよう検査されます。

決定論的な部分——状態機械・監査ログ・並列エージェントを裁く referee——は全ハーネスでバイト同一です。 違うのは殻だけ。だから「Claude Code で確立した挙動が Codex では違う」という事態が構造的に起きにくくなっています。

"harness" という語が3つの意味で使われる

リポジトリを読むときの罠です。harness/（配布表層）、docs/harness-engineering/（カスタマイズ担当者向けガイド）、 tests/harness/（テストのヘルパライブラリ）は、互いに無関係です。

3.3つのプレーンとコンパイル境界

AI-DLC はネットワーク機器の設計を明示的に借りています。この比喩を掴んでおくと、後述の挙動が全部説明できます。

プレーン中身ネットワークでいうと
Control plane何が走るべきかのスキーマ。ステージ定義、ルール、センサー経路計算。1回しか走らないので、遅くて賢くてよい
Data plane実際の実行。ステージ実行、エージェント起動、記録ディレクトリのファイルパケット転送。速く、繰り返し、ルックアップで
Management plane観測と設定。--doctor、監査ログ、CLAUDE.md人間のペースで触る面

control plane はワークフロー開始時に1回だけ、ルールとセンサーとステージ定義を1つのグラフにコンパイルします。 以降 data plane は解決済みの答えを読むだけで、チェーンを再帰的に辿り直しません。

ここから直接導かれる仕様が、第1部でも触れた 「ゲートで記録した学びは実行中のワークフローには効かず、次回から効く」です。 BGP が飛行中のパケットのために経路を再計算しないのと同じ理由で、AI-DLC はワークフローの途中で再コンパイルしません。 見返りは再現性と、リスタート後のクリーンな復旧です。序盤に承認したゲートの前提が、後から書き換わらない。

カスタマイズ時の実務的な意味

ルールやステージを編集したら、効果を見るには新しいワークフローを開始する必要があるということです。 ハーネスによってはスキル・エージェント・ルールをセッション開始時にロードするので、dist/ を入れ替えた場合は セッションごと再起動してください。公式トラブルシューティングにも「新しいセッションを開始せよ」と書かれています。

4.ステージファイルの解剖

ステージはワークフローグラフのノードであり、カスタマイズの原子です。 core/aidlc-common/stages/<phase>/<slug>.md という1つの Markdown ファイルで、YAML frontmatter とプロース本文からなります。

読者は2人いて、決して重ならない

  • パーサは frontmatter だけ読む。グラフのエッジ、リードエージェント、実行モードを取り出し、本文は完全に無視する
  • エージェントは本文 だけ読む。手順に従い成果物を作り、frontmatter には触らない

なぜ1ファイルに同居させるかというと、レビュアーが「何を produce するか」と「それを作る手順」を同時に見られるからです。 YAML とプロースを別ファイルに割ると、この可読性が失われる。ステージがレビュー可能であることを設計上の性質として守っています。

そして編集者にとっては、これが「今なにを変えたか」の判別基準になります。 frontmatter を変えたらグラフを変えたことになり、本文を変えたら仕事の中身を変えたことになる。この2つは独立です。

実物を見る（inception/application-design.md）

判断を要するフィールド

フィールド決めること判断のポイント
requires_stage依存と順序のエッジ本当に他ステージの出力を消費するのか、それとも単に「後に走ればよい」だけか。後者も表示順エッジとして明示的に書く（アルファベット順のタイブレークに任せない）
consumes読む成果物required: true は「このワークフローで生産元ステージが走るなら満たされていること」であって「生産元が常に走る」ではない。スコープは上流を意図的に飛ばす
produces書く成果物（前方エッジ）他ステージが「この成果物を作るのは誰？」と聞いたときの答えになる
lead_agent / support_agents誰がやるかcore/agents/*.md の実ファイルに対して検証される。ハードコードされた列挙はない
mode通信トポロジ誰が参加するかは support_agents、どう参加するかが mode
for_each反復するかインスタンスごとに1回走らせる成果物名。Construction の5ステージが for_each: unit-of-work を宣言。集約はグラフから推論され、宣言しない
scopesどのスコープで走るかこれを書かないとどこでも SKIP。ステージの存在と実行は別の関門

mode（トポロジ）の4種

mode意味採用ステージ
inlineconductor 自身のコンテキストで走る。サポートは「被るペルソナ」として同居28ステージ
subagentハブ&スポーク。リードを新鮮なコンテキストに委譲し、サポートは互いに盲目なスポークとして起動2（practices-discovery, code-generation）
pipelineチェーン。サポートを宣言順に連結し、各リンクは上流の成果を全部見る1（reverse-engineering の2リンク）

pipeline と mob は support_agents が非空であることを要求します。どのトポロジでも委譲は必ず conductor が行い、エージェント同士は呼び合いません。

本文の3コンパートメント

本文は必ずこの順で3つに分かれます。

  • ## Steps — エージェントが従う命令形の散文。ペルソナのロード、先行コンテキストの読み込み、質問ファイルの作成、成果物生成、承認ゲート。グラフを触らずに仕事の中身を変えたいときはここだけ編集する
  • ## Sensors — 出力に紐づく決定論的チェックの人間向け説明。実際の束縛は frontmatter の sensors: リスト
  • ## Learn — 学習ループの儀式。ステージ中につける memory.md 日誌と、ゲートで確定した項目の行き先
重要な境界

ステージファイルは形がイミュータブルなフレームワーク成果物です。 ワークフローが本文の3コンパートメント構造を書き換えることはありません。 実行中に許されている唯一の書き込みは、学習ループが frontmatter の sensors: に新しいセンサー ID を追記することだけ。 それ以外の変更は、あなたがカスタマイズ担当者として意図的に行うものです。

なお、ステージが含むもの（＝ファイル形式、この章）と、ステージが実行時にすること（＝承認ゲート、質問フロー、状態チェックボックス、完了メッセージ）は別契約です。 後者は全ステージ共通の stage protocol で、ステージ本文の「Follow stage-protocol.md」はこれを指しています。 定義は編集するもの、プロトコルは基本的に放っておくものです。

5.グラフのコンパイル

依存グラフはどこにも直接書かれていません。全ステージの consumes / produces 宣言から創発します。 実行時に読まれるのは、そこからコンパイルされた2つの JSON です。

コンパイル時に自動で検証されること

  • グラフ配置：エッジ解決、トポロジカル順序、生産者／消費者ルックアップ、循環検出
  • frontmatter のフィールド検証：lead_agent / support_agents は loadAgents() で実ファイルに照合される。タイポは「実行時に404する不正なグラフ」ではなくコンパイル失敗になる
  • 命名規則：ファイル名の stem と frontmatter の slug の不一致、slug の重複はハードエラー。センサーの ID 不一致も同様
  • フェーズルールの接続：ステージはディレクトリでフェーズを宣言しているので、対応する phases/<phase>.md が自動で接続される
  • ドリフトガード：compile --check はクリーンなら 0、YAML を編集して JSON を再生成し忘れていれば 1

自分で確認しないといけないこと

  • スコープ参加：コンパイラはグラフに置くだけで、どのスコープで走るかは決めない。scopes: を書くまで、グラフに存在するがどこでも走らない
  • 本文とエッジの整合：パーサはエッジしか見ない。「intent statement を読め」と本文に書いたなら、その生産元が requires_stage に入っている必要がある。手で同期する
  • 上流不在時の挙動：required: true の consume は、生産元を飛ばすスコープでは無効化される。それは仕様であってバグではないが、本文がその不在を優雅に扱うかは書いた人の責任
  • ドキュメント：ステージ数など手書きで列挙している表があるので、同じ変更の中で更新する（リポジトリの Documentation Policy）

グラフの検査コマンド

# トポロジカル順序（追加した slug が出るか）
bun .claude/tools/aidlc-graph.ts topo

# この成果物を作る／読むのは誰か
bun .claude/tools/aidlc-graph.ts producers <artifact>
bun .claude/tools/aidlc-graph.ts consumers <artifact>

# あるスコープの経路上にいるステージ
bun .claude/tools/aidlc-graph.ts scope <scope-name>

# そのスコープの依存が破綻していないか
bun .claude/tools/aidlc-graph.ts validate-scope <scope-name>

6.カスタマイズの入口（全体地図）

公式ドキュメントは読者を3つに分けています。この区別が、そのまま「どこまでならコードを書かずに済むか」の地図になっています。

ガイドあなたは…変えるのは…
User GuideAI-DLC を使ってソフトを作る何も変えない。/aidlc を打ち、ゲートで答え、成果物をレビューする
Harness Engineer GuideAI-DLC の振る舞いをチームに合わせるフレームワークが読むデータ：ステージ、エージェント、スコープ、ルール、センサー、知識NO CODE
Developer ReferenceAI-DLC 自体を変えるそのデータを読むコード：orchestrator、フック、CLI ツール、コンパイルパイプライン、テストCODE

境界の判定は単純です。YAML frontmatter つきの Markdown か JSON 設定なら、データ側。.ts を開いた瞬間にコード側。 「ステージ追加」「エージェント追加」「スコープ定義」が TypeScript 不要であることは、フレームワークの設計原則として明言されています。

入口の一覧

やりたいこと書く場所効き方
ステージの仕事内容を変えるcore/aidlc-common/stages/<phase>/<slug>.md の本文そのステージのみ

1行だけ性質が違うのがチーム知識です。これは core/ の一部ではなく、あなたのプロジェクト内・実行時のディレクトリで、 フレームワークが上書きすることはありません。他はすべてフレームワークのソースとして core/ に書きます。

7.レシピ：ステージ／エージェント／スコープ

A. ステージを1つ足す

そもそも新ステージが要るかを先に問うこと。既存ステージがやっていない成果物を produce する、あるいは既存がカバーしない形で consume する場合に限って正当化されます。「手順の文言を変えたい」「リードエージェントを差し替えたい」「センサーを付けたい」だけなら、既存ファイルをその場で編集すれば十分です。

  1. フェーズを決める。ディレクトリがフェーズであり、これは飾りではない。コンパイル時にどの phases/<phase>.md ルール層が接続されるかを決める
  2. ファイルを作る。ファイル名の stem が slug であり、slug はエッジ・ジャンプ・監査ログ・スコープ表のすべてで同一性になる。後から改名すると波及するので慎重に
  3. エッジを配線する。requires_stage / consumes / produces の3つが互いに整合していれば、コンパイラが自動で位置を決める
  4. 再生成する：bun scripts/package.ts（インストール済みツリーで反復するなら bun .claude/tools/aidlc-graph.ts compile）
  5. どのスコープで走るか決める。scopes: に書いて再コンパイル。書くまでは走らない

ここが v2 の拡張性契約の核心です——ステージを足すとは、ステージファイルを1つ書くこと。それ以外に構造上必要なものはありません。コンパイルが通れば、その時点で単体実行できます。

bun .claude/tools/aidlc-orchestrate.ts next --stage <your-slug> --single

--single は意図的に隔離されていて、メインワークフローの Current Stage を絶対に動かしません。進行中のワークフローを単体実行で脱線させることは起こり得ない設計です。

runner スキルは任意の砂糖

出荷されている各ステージには skills/aidlc-<slug>/SKILL.md という薄い runner があり、/aidlc-application-design のように打てます。 これは --single フラグの opt-in なラッパー（6行程度のシェル）で、手書きではなくジェネレータが出力します。 だから runner の集合とステージの集合が手作業でズレることがありません。 

bun .claude/tools/aidlc-runner-gen.ts write   # 再生成
bun .claude/tools/aidlc-runner-gen.ts check   # ドリフトガード（不一致なら exit 1）

runner に hooks: ブロックはありません。決定論的スパイン（監査・センサー・グラフ再構築・状態検証）は settings.json にプロジェクト全体で登録されているので、全 runner がタダで継承します。

B. エージェントを足す

core/agents/<slug>.md にファイルを置くだけです。ハードコードされたエージェント列挙は存在しません—— ステージの lead_agent / support_agents は loadAgents() で実ファイルに照合されます。

ステージとエージェントの関係は非対称です。ステージはリードエージェントを名指しするが、エージェントは自分のステージを名指ししない。 これは意図的で、作業の割り当てを変える（ステージを編集）ことと 働き手を増やす（エージェントファイルを置く）ことを独立にできます。 エージェントを足しても、どこかのステージが使うと決めるまでワークフローは何も変わりません。

モデルと effort の tier

出荷エージェントは tier:（judgment / balanced / templated）を持ち、ビルドが各ハーネスのモデル／effort キーに射影します。

  • judgment — セッションのモデルと effort をそのまま継承。あなたが選んだものより下げられることはない。architect・product・design・developer・quality・devsecops・compliance・aws-platform の8体
  • templated — 中型モデル＋低 effort（Kiro 以外）。delivery・pipeline-deploy・operations の3体。出力が計画・CI/CD YAML・ランブックの雛形に偏っているため

1体だけ変えたいなら、インストール済みの .claude/agents/aidlc-*-agent.md の frontmatter を直接編集（例：model: opus）。 ただし dist/ を再コピーすると消えます。 全体を上限で縛るなら core/memory/ の tier_cap: か、パッケージャの環境変数 AIDLC_TIER_CAP——どちらもパック時のノブで実行時設定ではありません。

やってはいけないこと

出荷済み14エージェントのファイルに自社の知識を書き足さないでください。フレームワークファイルなのでアップグレードで上書きされます。 自社標準はスペースレベルの aidlc/knowledge/<agent-name>/ に置く。新しいエージェントを足すのは自由で、そのファイルはユーザー所有です。

C. スコープを定義する（hotfix の例）

スコープは2つに分かれて書かれます。この分割自体が要点です——スコープの同一性は自分のファイルに、所属はステージ側に転置して置く。

1. スコープファイル core/scopes/aidlc-hotfix.md：

---
name: hotfix
depth: Minimal
keywords: [hotfix, urgent]
description: 緊急の本番パッチ。回帰テストとデプロイだけ
skeleton: off
testStrategy: Minimal      # 省略すると depth を継承
review_cap: advisory       # ステージのレビュー階級を下げる（上げることはできない）
runner: true               # /aidlc-hotfix を生成させる場合
---

# hotfix scope

なぜこれらのステージを走らせ、なぜ他を飛ばすのかの散文。

2. 所属タグ：走らせたい各ステージの frontmatter scopes: に hotfix を足す。タグしなければ SKIP。Initialization の3ステージは必ず含める（常に走るため）。

3. 再コンパイルと確認：

bun .claude/tools/aidlc-graph.ts compile          # scopes: を grid に転置
bun .claude/tools/aidlc-utility.ts scope-table    # SKILL.md の表を更新
bun .claude/tools/aidlc-graph.ts compile --check  # exit 0 を確認
/aidlc --doctor

keywords を入れた場合は、その語を含む自由文が feature に落ちずに新スコープを検出することを確認します。 逆に、composer が自動生成したスコープは keywords: [] で出荷され、一回きりの計画がキーワード検出に混ざらないようになっています。 将来の自動検出対象にするかはゲートで明示的に聞かれる質問であって、副作用では起きません。

スコープは /aidlc --scope hotfix でファイルを置いた瞬間から使えます。runner: true は 1語コマンド（/aidlc-hotfix）が欲しいときだけの砂糖です。

8.レシピ：ルール・センサー・知識

ルール — 5層の strict-additive チェーン

aidlc/spaces/<active-space>/memory/
├── org.md          フレームワーク + 組織全体の既定
├── team.md         チームが是認したプラクティス
├── project.md      このプロジェクト固有
└── phases/
    ├── ideation.md  inception.md  construction.md  operation.md

ファイル内に scope: フィールドはありません。スコープはファイル名から来ます。 解決順は org → team → project → phase → stage（第5層のステージ別ルールは将来枠）。

モデルは strict-additive です。適用対象のルールはすべてエージェントのコンテキストに現れ、実行時に黙って落とされたり上書きされたりしません。 overrides: ブロックも enforcement: キーワードも v2 にはもう存在しません。

では矛盾はどう処理するか。書き込み時に捕まえます。 確定した学びがディスクに落ちる前に、org.md の同じ見出しに対してセクション単位のチェックが走り、 矛盾していればゲートが止まって衝突している org の文をその場で引用します。 選択肢は「書き直す」「見送る」「org ルールのオーナーにエスカレーション」。 矛盾を含んだルールがディスクに乗らないので、実行時のリゾルバは単純なままでいられます。

org ポリシーが後から変わって既存の team/project ルールと衝突した場合は、/aidlc --doctor がドリフトとして報告します（助言的、ブロックしない）。

学習ループが書き込む先

ゲートで確定した学びの行き先は、あなたが選ぶのではなく見出しが決めます。 Interpretations / Deviations / Tradeoffs は project.md にプラクティスとして着地。Open questions は昇格しません（調査項目であってルールではない）。 既定スコープは常に project で、「team に昇格」はワンクリックの明示操作。org への昇格経路は存在しません—— 1プロジェクトの驚きが組織全体のルールになる事故を防ぐためです。

センサー — pull authoring

センサーはマニフェスト（core/sensors/aidlc-<id>.md）＋必要ならスクリプトで、 ステージ側が sensors: リストで取り込む形（pull）です。センサーがステージを名指しするのではありません。

発火は PostToolUse フック経由。エージェントがステージの出力ファイルを Write / Edit したときに、 そのステージに紐づくセンサーのうちファイル形状がマッチするものが走ります （**/*.{ts,js} を宣言したコード品質センサーは TS/JS の書き込みにしか反応しない）。

出荷センサー発火対象チェック内容
claim-sourcesIntent Capture の出力全主張にソースタグがあるか、登録情報が権威ある入力と一致するか、保持された仮定が明示確認と厳密一致するか
required-sections記録ディレクトリの md 出力必須の H2 見出しが存在するか（汎用の内容形状チェック）
upstream-coverage同上成果物群が、宣言した上流成果物それぞれを slug / wikilink / ディレクトリパスで参照しているか
linter.ts / .js設定済みリンタ（既定 ESLint）のラッパー
type-check.ts / .tsx設定済み型チェッカ（既定 tsc）のラッパー

現行版ではセンサー結果は助言的です。失敗しても承認ゲートを止めません。監査行と、何が欠けているかを指す詳細ファイル （<record>/.aidlc-sensors/<stage>/...）が残るだけ。シグナルは出す、判断は人間、という構えです。

学習ループがセンサーを提案してきた場合の install はアトミックな2書き込みです： マニフェストを scaffold し、発火元ステージの import リストに ID を追記する。 SENSOR_PROPOSED / RULE_LEARNED の監査行が残るので、黙って install されることはありません。

知識 — 2層構造

Tier 1：方法論知識

フレームワーク同梱。.claude/knowledge/<agent>/。AI-DLC のやり方そのもの。触らない。

Tier 2：チーム知識

あなたが足す。スペースレベルの aidlc/knowledge/<agent>/。自社標準・命名規約・ドメイン語彙。フレームワークは上書きしない。

ルールと知識の使い分け：ルールは「常にこうせよ」という制約で、strict-additive にコンテキストへ載る。 知識は「この領域はこうなっている」という情報で、担当エージェントが起動したときにロードされる。 「PII は必ずマスクする」はルール、「弊社の顧客マスタのスキーマはこう」は知識、という切り分けです。

9.プラグイン機構

「チーム固有の一式を配りたい」場合の答えがプラグインです。新しいステージ・エージェント・スコープ・ルール・センサー・知識、 そして既存 core ステージへの追加的な contribution を、独自のディレクトリ／独自のリポジトリにまとめて配布し、 ユーザーの install に合成します。

重要な保証が2つあります。

  • プラグインは core/ を編集しない。全プラグインを無効にすると、install は素の core とバイト同一に戻る
  • ファーストパーティとサードパーティは機構的に同一。同じ構造、同じ継ぎ目、同じコンポーザ、同じ保証。違うのは出自だけ
test-pro/                                       ← リファレンス実装
  .aidlc-plugin/plugin.json                     マニフェスト（宣言的）
  stages/construction/test-pro-integration.md   新規ステージ
  contributions/construction/nfr-requirements.md 既存 core ステージへの追加
  sensors/aidlc-coverage-threshold.md           新規センサー
  tools/aidlc-sensor-coverage-threshold.ts      そのスクリプト
  scopes/test-pro-validation.md                 新規スコープ
  agents/test-pro-metrics-agent.md              新規ペルソナ
  knowledge/test-pro-metrics-agent/methodology.md

命名の規律が効いています：

  • プラグインのステージは plugin: フィールドで自分の所属を名乗る
  • produces: する成果物は <plugin>- 接頭辞が必須
  • 合成側はプラグイン同一性を出荷されたホストマニフェストから導出する。中身が自分のパッケージ名を騙ることはできず、不一致は skip されて --doctor に記録される
  • number: は表示ヒントに過ぎない。グラフ上の位置は slug ベースの requires_stage エッジで決まり、番号はエンジンが割り当てる。だからプラグインは番号レンジを予約しない

install 側は bun .claude/tools/aidlc-utility.ts select-plugins <names> で有効化するプラグインを絞れます。 プラグインは足す、install が選ぶ——無効化してもファイルは残り、再有効化できます。

プラグインにすべきか、ただのステージ／ルールにすべきか

  • ステージ／エージェント／ルール — 全員が受け取るフレームワークの恒久的な一部にしたいとき
  • プラグイン — 任意で所有権のあるもの。自分のリポジトリで出荷し、opt-in のスコープ（あるいは when: 述語）でのみ起動し、利用者が選んで合成する。「コンプライアンスパック」「テストパック」のようなドメインパック向け

10.Construction：Bolt と swarm

Construction の形は、v2 で最も試行錯誤の跡が残っている部分です。公式ドキュメントが経緯を率直に書いています。

世代やり方問題
初期作業単位ごとにステージ単位で承認3ユニットで15ゲート。「子守り」と言われた
次全ユニットの質問・設計・コード生成を一括、最後に1回レビュー15ユニットだと 15,000 行が1つのゲートに来る。レビュー不能
現行Bolt 単位。1 Bolt ＝ 1ユニット（または依存で束ねた小グループ）に対する 3.1〜3.5 の1周——

ladder prompt

最初の Bolt は walking skeleton——アーキテクチャを端から端まで証明する最小のスライス——で、必ずゲートされます。 それが通った直後に、ワークフロー中ちょうど1回だけこの質問が出ます。 

自律で続行する？ それとも Bolt ごとにゲートする？

答えは aidlc-state.md に Construction Autonomy Mode として記録され、残り全 Bolt を支配し、セッション再開時にも尊重されます。 早い段階での確信チェックポイントと、意図的な自律性の選択を1回だけ迫る設計です。

並列バッチと halt-and-ask

2つの Bolt が同じ依存前提を共有していて互いに依存しないなら（B も C も A にだけ依存する等）、 1つのバッチとして並行実行され、バッチ末尾の1ゲートが両方をカバーします。 conductor は1ターンで複数の Task を発行し、ハーネス組み込みの並列性でコード生成を同時に走らせます。 質問収集と設計成果物生成は Bolt ごとに直列のままです（安いし、質問の答えはどのみち人間を通して直列化されるため）。

失敗は自律モードでも必ず止まります。これが自律モードで唯一割り込む場所です。 単独 Bolt の失敗は即停止して retry / skip / abort を提示。 並列バッチ中に1つだけ失敗した場合は、バッチ全体の完了を待ち、成功した Bolt の成果物をディスクに保全したうえで、 失敗した Bolt についてだけ同じ選択を出します。

11.composer と in-flight recompose

既存スコープがどれも当てはまらないとき（キーワードなしのリッチな散文、長い説明の中に埋もれたキーワード）、 /aidlc は黙って feature に落とさず、専用計画の作成を提案します。 

/aidlc compose "デプロイパイプラインを堅牢化し、可観測性を追加する"
/aidlc compose --report sonar.json     # スキャンレポートから構成
/aidlc --new-scope "..."               # 既存スコープに合致しても強制的に custom

composer は実装エントロピーの5成分——意図の曖昧さ、コードベースの構造的不確実性、検証エントロピー、リスク、未解決の仮定——を見積もり、 成果が依存する成果物をすべて生みながら最小で足りる EXECUTE/SKIP グリッドを組みます。

提示されるのは、各成分の LOW/MED/HIGH バンドと根拠、助言的な合成スコア、そして 全ステージについて EXECUTE と SKIP の理由を書いた表。承認・編集・却下が選べ、明示承認の前に何も書かれず、ワークフローも始まりません。

承認後の挙動は2通り：

  • 提案が既存スコープに MATCH していれば、そのスコープでワークフローが誕生する
  • CUSTOM グリッドなら、composer が実物のスコープファイル（scopes/aidlc-<name>.md ＋ grid エントリ）を書き起こし、同じターンでそこから誕生する。以後は普通のスコープと同様に --scope <name> で解決でき、グラフ再コンパイルを生き延びる（compile が合成済みエントリを再生成後のグリッドに畳み戻す）

実行中の再構成

ワークフローの途中でも /aidlc compose は未実行ステージの再構成を提案できます。 完了済みステージが実際に解決したことを踏まえてエントロピーを再見積もりするので、各フリップは根拠を名指しします （「実現性検討で連携の疑問が片付いた → リスクは MED に再スコア」）。

制約は明確です：

  • フリップできるのはカーソルより先の未実行ステージだけ。完了済みと実行中は凍結
  • strict 検証を通るので、残ステージが必要入力を失うことはない
  • 決定論的な recompose 動詞を通り、監査ロックの下で RECOMPOSED イベントを残す
  • Construction の最初の EXECUTE ステージ（walking-skeleton ゲートのアンカー）はフリップできない

リテラルな動詞は必須ではありません。「market research は要らないんじゃない？ この市場は分かってるし」のような普通の会話も、 実行中は再構成要求として認識され、同じゲート・同じ検証・同じ recompose 動詞を通ります。

12.決定論的スパイン：フックと監査

core/hooks/ に 17本のフックがあり、すべて aidlc-*.ts で bun 実行されます。 性質は2つに分かれます。

種別フック役割
フロー制御系
（止められる）		 aidlc-continue-workflow（Stop）転送ループを決定論的に保証する（§1）
aidlc-deliver-stage-rulesステージルールの正確な配送を強制
aidlc-plan-approval-guardコード生成の計画承認を強制
aidlc-state-transition-guard状態の直接遷移を禁止

監査は 82種類のイベント型で、インテントの audit/ シャードに構造化ログとして書かれます。 STAGE_STARTED / GATE_APPROVED / GATE_REJECTED / RULE_LEARNED / SENSOR_PROPOSED / RECOMPOSED / HUMAN_TURN など、 この資料で説明してきた挙動はすべて監査行として観測可能です。研究会で挙動を追うなら、ここが一番の観測点になります。

承認の偽造防止

第1部でも触れた仕掛けを、実装の言葉で書き直しておきます。 人間がプロンプトを打つ／選択ウィジェットに答えると HUMAN_TURN イベントが台帳に記録されます。 承認（および明確化質問への回答）は、前回のゲート解決以降に HUMAN_TURN が1件も記録されていなければ拒否されます。 自動運転のモデルが「承認されました」を自作自演できません。

（ゲートウィジェットが人間ターンを記録しないハーネスでは、一度「approve」と打てば記録される。台帳に人間ターンがまだ存在しないハーネスでは fail open。）

テストの層

bun tests/run-tests.ts             # 既定：smoke + unit + integration
bun tests/run-tests.ts --ci        # CI と同じ
bun tests/run-tests.ts --release   # + e2e（完全受け入れ）

全 TypeScript で、t*.test.ts の命名。ドキュメントと実装の同期もテストで縛られています—— たとえばスコープ×ステージのマトリクス表は tests/unit/t244-scope-matrix-doc-sync.test.ts がコンパイル済みグリッドと突き合わせます。 バージョン・CHANGELOG・README バッジの一致は t68 が縛る。 ドキュメントを「テストされる成果物」として扱っているのは、この手のフレームワークとしては珍しい部類です。

13.落とし穴集

1. dist/ を直接編集

ドリフトガードが CI を落とします。編集は必ず core/（または harness/<name>/）。core/ の編集と再生成した dist/ は同じコミットに入れる。

2. scopes: タグ忘れ

ステージを足してコンパイルが通っても、scopes: を書かないとどこでも走りません。「存在させる」と「走らせる」は別の関門。

3. 実行中の反映を期待する

ルールもステージ定義もワークフロー開始時に1回コンパイル。編集の効果は次回から。dist/ を入れ替えたらセッションごと再起動。

4. 出荷エージェントに知識を書き足す

アップグレードで消えます。aidlc/knowledge/<agent>/ に置くか、新しいエージェントファイルを作る。

5. slug の後付け改名

slug はエッジ・ジャンプ・スコープ表・監査ログ全部で同一性。改名は全方位に波及します。最初に決める。

6. 本文とエッジの乖離

パーサはエッジしか見ません。「〜を読め」と本文に書いても requires_stage になければ、そこにファイルは無い。手で同期する。

7. コンパイラ未実装のキーに手を出す

when: / on_failure: / blocks_on: 等は予約済みだが未実装。スキーマが拒否します。欲しくなった時点でそれはコード変更。

8. bun が非対話 PATH にいない

フックとツールは非対話シェルで走ります。ターミナルで which bun が通るのにハーネスが見つけられない場合、export を ~/.zshenv / ~/.bashrc に写す。

9. 出荷時の設定が AWS 前提になっている

dist/claude/.claude/settings.json は CLAUDE_CODE_USE_BEDROCK=1 / AWS_REGION=us-east-1 と Bedrock のモデル ID を固定しています。 Bedrock のモデルアクセスと AWS 認証情報がないと起動しません。 手元のハーネスの認証をそのまま使いたい場合は、.claude/settings.local.json（gitignore 対象）で env の Bedrock 関連キーを除去します。 AWS_AIDLC_DEFAULT_SCOPE は Bedrock とは無関係なので残して構いません。

同様に .mcp.json は context7（要 API キー）と AWS 系4本（要 uvx ＋ AWS 認証）を宣言しています。 認証のないサーバは単に使えないだけでワークフローは止まらないので、必要になるまで導入しない選択もできます （composer の CodeKB グラウンディングは、MCP がなければワークスペーススキャンにフォールバックする、というのが正常系です）。

14.研究会向け実験メニュー

実際に手を動かすなら、この順で触ると構造が腹に落ちやすいはずです。 本番リポジトリではなく空のワークスペースを用意し、配布物をコピーした直後に git init ＋ タグを打っておくと、 git reset --hard <tag> && git clean -fd でいつでも初期状態に戻せます。 フレームワーク自身の書き込みと生成された成果物を git diff で切り分けられるので、観察目的でもこの形が扱いやすいです。

議論したい論点

  • ルーティングを決定論に置く判断は、どこまで一般化できるか。「経路計算はコード、実行品質は LLM」という分割は AI-DLC 固有か、それともエージェント設計の一般原則か
  • コンパイル境界（実行中は再コンパイルしない）は、正しいトレードオフか。再現性を取って適応性を捨てている。長いワークフローほど代償が大きい
  • センサーが助言的であること。ブロックしないなら、失敗はどこで回収されるのか。ゲートの人間に依存していないか
  • 32ステージという粒度。スコープで削れるとはいえ、既定のセットは AWS の想定するプロジェクト像に強く紐づいている。自分たちの現場に写すとき、何を捨てて何を足すか
  • プラグイン機構を使う価値があるのはどの規模から。core/ をフォークして直接いじるのと、プラグインとして分離するコストの分岐点
